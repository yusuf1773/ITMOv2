# Исследование и решения: mate-in-one-backend

## Сводка (Summary)

- **Дата:** 28 октября 2026 года.
- **Спецификация:** mate-in-one-backend.
- **Тип исследования:** новая функциональность, полное discovery по kiro-spec-design.
- **Основание:** требования утверждены пользователем; [общий контракт](../../contracts/mate-in-one-api.md) уже утверждён и включает исправленное правило превращения.
- **Ключевые результаты:** приложение остаётся простым, локальным и синхронным; отдельные потоки и фоновые задачи не нужны. Фабрика Flask отделяет запуск и готовность данных от обработки запроса. Шахматные правила делегируются chess; новая доска на попытку обеспечивает независимость. Подготовка пяти собственных учебных позиций включена в будущую работу backend.
- **Границы доказательств:** сейчас созданы только документы. Зависимости Flask/chess не установлены, приложение не запущено, FEN учебного набора не созданы и не валидированы. Исследование документации не подменяет будущие проверки.

### Шахматный API и превращение

Критичные решения на основании [официального Core reference](https://python-chess.readthedocs.io/en/latest/core.html):
- Конструктор доски и её проверка валидности — разные действия. Нужны синтаксическая проверка FEN, is_valid/status, проверка завершённости и существования матующего хода.
- Доска изменяема. Создавать её заново для каждой попытки; применять ход только после проверки допустимости. Для исследования всех решений использовать независимые копии.
- find_move может автоматически выбрать ферзя: этот helper исключён из обработки согласованного promotion:null.
- Ветка обычного хода проверяется раньше ветки превращения; явная фигура не подменяется.
- Полный FEN результата формируется с явным en_passant="fen", чтобы настройка по умолчанию не скрывала целевое поле взятия на проходе.

Остальные решения — выводы проектирования из требований, а не новые возможности библиотеки: список допустимых ходов остаётся внутренним, найденные решения не публикуются, исходный FEN хранится отдельно от изменяемой доски. Ретроспективная достижимость за всю историю партии не обещается; исторических повторений из FEN узнать нельзя. Claimable draw не добавляется в интерфейс тренажёра.

### Flask: фабрика и порядок ошибок

Источники: [Application Factories](https://flask.palletsprojects.com/en/stable/patterns/appfactories/), [Handling Application Errors](https://flask.palletsprojects.com/en/stable/errorhandling/), [Request.get_json](https://flask.palletsprojects.com/en/stable/api/#flask.Request.get_json).

Фабрика нужна для замены конфигурации и тестовых данных без глобального пользовательского состояния. Ошибки 404/405 регистрируются на уровне приложения; сериализация сохраняет статус и служебные заголовки. Проверки тела выполняются после маршрутизации, готовности набора и ID. Не используются force/silent-разбор, скрывающий различие Content-Type и неверного JSON. Для согласованного application/json проверяется нормализованный mimetype, а не широкое is_json. Разобранный JSON null — ошибка структуры, а не синтаксиса.

Технические HEAD/OPTIONS остаются стандартным поведением Flask; собственная реализация или новые бизнес-маршруты для них не проектируются. Для неразрешённого PUT проверяется 405 прежде готовности. У HEAD нет тела даже при ошибке; тест не должен ожидать JSON-тело. Согласованный UI использует только GET/POST и не нуждается в CORS-preflight.

### Готовность набора и локальный запуск

Нельзя просто выбросить исключение фабрики на дефекте задач и затем обещать JSON 503 от того же несуществующего процесса. Выбрано состояние каталога Unavailable в работающем HTTP-приложении: поддерживаемые операции возвращают 503, а 404/405 сохраняют более высокий приоритет. Ошибки данных логируются оператору. Отсутствие запущенного процесса остаётся сетевым сбоем, как в контракте.

Это проектное решение следует из раздела 8 контракта. Горячая перезагрузка, фоновый watcher и частичное обслуживание каталога не нужны; смена набора выполняется перезапуском и полной проверкой.

### Поставка UI с одного origin

UI-команда отвечает за исходники и поведение интерфейса. Пользователь утвердил единую структуру: UI_ROOT указывает на frontend; GET / отдаёт frontend/index.html; /static/ui/styles.css отдаёт frontend/styles.css; /static/ui/js/... отдаёт соответствующие файлы frontend/js/.... API остаётся /api/v1. Универсальная раздача всего frontend запрещена: frontend/tests и frontend/package.json остаются непубличными. Фабрика отключает автоматическую раздачу статического корня и регистрирует только утверждённые маршруты, сохраняя безопасное разрешение пути JS внутри frontend/js. SPA-fallback для неизвестных API-путей отсутствует.

Сценарии навигации, выбора фигуры, десятисекундного ожидания и поздних ответов проверяются совместно с mate-in-one-ui. Тестовая поставка проверяет маршрутизацию и ограничения доступа, но не готовность реального UI. До передачи UI API может проверяться отдельно. Совместная приёмка требует настоящих frontend/index.html, styles.css, app.js и всех импортируемых модулей; проверяются байты, MIME и отсутствие сбоев загрузки, а не только 200 для страницы. На существующих файлах frontend/tests и package.json подтверждаются 404 по прямым URL и невозможность выхода из JS-каталога; одних отсутствующих файлов для проверки запрета недостаточно.

### Подготовка пяти позиций

Ранее не был определён поставщик позиций. В текущем запросе пользователь прямо потребовал предусмотреть подготовку и проверку; дизайн включает ручную подготовку пяти собственных простых позиций в будущую реализацию backend, без внешнего поставщика и без генератора в приложении.

В design.md определены пять ID и учебные акценты, проверка всего набора, перебор всех допустимых матующих ходов, контрольные попытки, ручная проверка и отчёт с хешем JSON. Ответы решения сохраняются в непубличных фикстурах, исходные данные не содержат решений. Специальные случаи при необходимости добавляются в тестовые позиции, а не увеличивают число учебных задач.

Вывод: требования исполнимы без готового внешнего набора. Конкретные FEN готовит исполнитель на реализации и заменяет непригодные кандидаты; этот документ не выдаёт непроверенные FEN за валидный набор.

### Уточнение пользователя о потоках

В ходе подготовки пользователь указал, что приложение простое и локальное. Собственные потоки выполнения не требуются. Первоначальный многопоточный тест удалён из дизайна. Проверка независимости использует отдельные клиенты последовательно и отсутствие общего изменяемого объекта доски. Неизменяемый каталог и новая доска на вызов сохраняют независимость и при перекрытии обычных запросов сервера, без собственного управления потоками.

Название System Flows из шаблона означает схему последовательности обработки; в документе оно пояснено как «Сценарии обработки». Очереди, asyncio, исполнители фоновых работ и специальный многопоточный запуск не вводятся.

## Проектные решения (Design Decisions)

### Решение: простое синхронное выполнение

Обычные Flask-обработчики вызывают загрузчик и шахматную проверку без фоновых процессов. Это соответствует локальному масштабу и уточнению пользователя. Одна попытка мала и не требует внешнего движка. Ограничение ожидания остаётся в UI.

### Решение: использовать готовые шахматные правила

Выбран chess; собственные правила перемещения, шаха, превращения, рокировки и взятия на проходе не пишутся. Собственный код отвечает только за согласованный порядок проверок и отображение результата. Внешний шахматный движок исключён ограничениями пользователя.

### Решение: типы без лишних абстракций

Достаточно frozen dataclass, Literal и объединений результатов. Не вводятся DI-контейнер, интерфейс для гипотетического второго хранилища или общий валидатор бизнес-правил. Один загрузчик, один проверяющий компонент и HTTP-граница.

### Решение: обобщение на уровне входа, не расширение объёма

Один механизм проверки по FEN обслуживает попытки и проверки пригодности. API не получает новые операции анализа, подсказок или генерации. Список решений используется только при подготовке/проверке данных.

### Решение: неизменяемый снимок и доска на попытку

Хранится проверенный FEN, не разделяемая Board. Повторы не меняют состояние, нет сессии и ключа идемпотентности. Валидация набора атомарна; обновление через перезапуск. Следствие — простые условия восстановления и проверки исходных данных.

### Решение: отдельная ответственность UI

Same-origin означает совместное обслуживание, а не разработку UI backend-командой. Все клиентские критерии прослежены до совместной приёмки и файловой поставки mate-in-one-ui.

## Риски и меры (Risks & Mitigations)

- Ошибка автоматического превращения: не использовать find_move; отдельные тесты обычного null и всех четырёх явных фигур.
- Непроверенные задачи: подготовка пяти позиций обязательна, перед запуском полный контроль и хотя бы один мат у каждой; неверные кандидаты заменяются.
- Утечка решений и тестовых материалов: runtime-данные и backend-фикстуры вне UI_ROOT; frontend/tests и package.json внутри frontend исключены из публичных маршрутов. Маршруты не сериализуют PositionReport. Запрет проверяется на существующих файлах и попытках обхода путей.
- Изменение FEN при нормализации: исходный FEN сохраняется, результат формируется явно; проверить ep-поле отдельной фикстурой.
- Неверный приоритет 404/503/400: матрица конфликтов, без разбора тела до готовности и ID.
- Недоступная UI-поставка: API-тесты используют тестовую поставку; полноценная интеграция требует реальных файлов и не объявляется готовой заранее.
- Переусложнение: никаких собственных потоков, фоновых задач или дополнительных runtime-сервисов.
- Отсутствие зависимостей: изолированная установка и живой smoke обязательны на реализации; документационный этап их не имитирует.
- Распространение с GPL-зависимостью: сохранить сведения о лицензии и проверить условия реальной поставки перед распространением.

## Проверка дизайна

Проведено ограниченное независимое ревью исследовательским агентом: блокирующих находок по контракту, превращению, готовности, правилам шахмат и UI-границам нет. После уточнения пользователя дизайн упрощён: удалён многопоточный тест; стандартные технические методы Flask не обрастают собственной бизнес-реализацией. Окончательная проверка в основном контексте контролирует все 82 точных ID, конкретные пути файлов и ответственность компонентов.

Это проверка документа, не утверждение дизайна пользователем и не свидетельство прохождения тестов приложения.

## Согласование единой передачи UI от 28 октября 2026 года

Основание: прямое утверждение пользователя и сопоставление с разделом интеграции design.md спецификации mate-in-one-ui. Единственная структура — frontend с маршрутом / и ресурсами /static/ui/styles.css и /static/ui/js/.... Отменена прежняя альтернативная схема каталогов и ресурсов. В backend-дизайне синхронизированы разрешённые зависимости, план файлов, AppRuntime, модель публичного доступа, безопасность и проверки. API /api/v1 и бизнес-контракт не меняются.

Простая универсальная раздача static_folder=frontend без ограничения путей не подходит: вместе с UI она могла бы открыть tests и package.json. Выбраны точные маршруты HTML/CSS и ограниченная раздача js; отдельный публичный тестовый маршрут не добавляется. Реальные файлы UI не копируются и не редактируются в ходе согласования.

Проверки после разрешения реализации: загрузка настоящей страницы и всех её CSS/JS-зависимостей с корректными MIME; сохранение /api/v1; отказ в доступе к существующим frontend/tests и package.json по прямым и обходным путям. На этом этапе проверено согласование документов, а не фактическая HTTP-раздача. Полный дизайн по-прежнему ожидает утверждения; код и tasks.md не создаются.
