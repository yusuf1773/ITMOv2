# Татарча Constitution

## Core Principles

### I. Сначала поведение, затем реализация
До выбора архитектуры, макета и кода команда MUST согласовать пользовательские сценарии,
ожидаемые результаты, ошибки и пограничные состояния. Спецификация MUST отделять
согласованные требования от предложений и открытых вопросов. Это позволяет проверять
реализацию по понятному контракту, а не по догадкам исполнителя.

### II. Основной сценарий работает целиком
Основной путь пользователя MUST завершаться реальным видимым результатом и сохранением
необходимого прогресса через действующую логику проекта. Каждое действие в этом пути MUST
иметь определённое поведение при успехе и сбое. Демонстрационный интерфейс без результата
не подтверждает выполнение сценария.

### III. Доступность и понятная обратная связь
Основной сценарий MUST выполняться с клавиатуры; элементы управления MUST иметь понятные
подписи и видимый фокус. Интерфейс MUST показывать пользователю результат действия,
состояния ожидания и ошибки понятным языком. Содержимое и управление MUST оставаться
доступными на узком экране.

### IV. Тесты проверяют действия пользователя
Автоматические тесты MUST проверять взаимодействия и видимые результаты, включая
некорректный ввод, ожидание, пустые данные, успех, ошибку и защиту от повторной отправки
там, где это применимо. Хотя бы один тест MUST проходить основной сценарий целиком.
Тесты MUST запускаться и проходить; само наличие тестовых файлов недостаточно.

### V. Проверенный учебный материал
Татарские слова, переводы, примеры и грамматические правила MUST опираться на проверяемые
источники. Источники MUST быть зафиксированы так, чтобы учебный материал можно было
проверить и исправить. Непроверенные сгенерированные примеры нельзя выдавать за факт.

## Project Constraints

Требования практики 8 и согласованные решения пользователя определяют объём проекта.
Открытые продуктовые вопросы MUST оставаться явно отмеченными как открытые. Технические
решения MUST быть обоснованы потребностью сценария; добавление серверной части само по
себе не является целью.

## Development Workflow

Работа идёт последовательно: обсуждение сценариев и состояний, согласование требований,
прототип, выбор стека и архитектуры, реализация, тестирование и материалы для сдачи.
Переход к следующему этапу требует согласия пользователя. Перед реализацией MUST быть
зафиксированы критерии приёмки; после реализации MUST быть проверены работающий интерфейс
и результаты тестов. Изменения поведения MUST сначала отражаться в согласованной
спецификации.

## Governance

Эта конституция задаёт принципы для спецификаций, планов, реализации и проверки проекта.
Изменения принципов MUST быть предложены пользователю и согласованы до применения.
Каждое изменение MUST фиксировать причину, затронутые принципы и новую версию:
MAJOR — несовместимое изменение принципов, MINOR — новый принцип или существенное
расширение, PATCH — уточнение без изменения смысла. При проверке каждого этапа MUST
сверяться соблюдение этих принципов и требований практики 8.
