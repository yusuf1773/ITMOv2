# Chain of Verification

- Проверяемый черновик или утверждение:
  - У1. «На уровне API — валидация тела запроса; 422 при отсутствии `diff`; 413 при `len(diff) > 20000` (API-1).» — Раздел: «Решение».
  - У2. «Перед LLM — модуль редактирования секретов, заменяющий токены/ключи на `[REDACTED]` (SEC-1).» — Раздел: «Решение».
  - У3. «Вызов LLM — с таймаутом 10 секунд и обработкой исключений; при срабатывании — контролируемый ответ (REL-1).» — Раздел: «Решение».
  - У4. «Формирование ответа — структура OUT-1: `summary`, `risks` (<=3 с `file`, `line`, `evidence`, `risk`), `checks`. Риски включаются только при подтверждении строкой diff или правилом (QA-1).» — Раздел: «Решение».
  - У5. «Логи содержат только `request_id`, длительность, статус (OBS-1).» — Раздел: «Решение».

## Запрос на проверку

Примени Chain of Verification к practices/practice_01/adr.md.

Проверяемый черновик — существующий ADR.
Единственный источник требований — practices/practice_01/CASE.md.

Не используй другие эксперименты, веб-поиск или предположения о не показанной реализации. Не изменяй ADR и не запускай тесты приложения.

Выполни следующие этапы последовательно.

Этап 1. Зафиксируй исходный черновик

Выбери 4–6 существенных утверждений из текущего ADR, которые можно проверить по CASE.md.

Для каждого сохрани:

- идентификатор: У1, У2 и далее;
- точную цитату ADR;
- раздел, из которого она взята.

Выбирай утверждения о маскировании секретов, ограничении размера diff, timeout, структуре ответа, доказательствах рисков или логировании.

Не придумывай утверждения и не исправляй цитаты на этом этапе.

Этап 2. Составь вопросы проверки

Для каждого утверждения сформулируй вопрос о фактическом требовании CASE.md.

Вопрос должен позволять получить ответ из первоисточника, не подсказывая желаемый вывод.

Примеры формы вопросов:

- Какие категории секретов требуется удалять перед отправкой во внешний LLM?
- К какой операции относится timeout и каково его значение?
- Какие поля ответа обязательны и сколько рисков допускается?

Не считай заранее, что в каждом утверждении есть ошибка.

Этап 3. Ответь на вопросы по первоисточнику

Повторно прочитай соответствующие фрагменты CASE.md.

Сначала ответь на каждый вопрос только по CASE.md, без обоснования через ADR. Для каждого ответа укажи:

- идентификатор вопроса;
- краткий ответ;
- номер правила;
- короткую точную цитату;
- ссылку на источник.

Если CASE.md не определяет запрошенную деталь, напиши «Источник этого не определяет». Не превращай отсутствие требования в запрет.

Только после подготовки ответов сопоставь их с исходными утверждениями ADR. Для каждого укажи итог:

- подтверждено;
- подтверждено частично;
- противоречит источнику;
- не установлено источником.

Кратко объясни конкретное совпадение или расхождение. Архитектурное решение, не установленное CASE.md, не обязательно ошибочно: его нужно обозначать как решение автора ADR.

Этап 4. Подготовь исправленный результат

Используя результаты проверки, подготовь минимальные исправления выбранных фрагментов ADR.

Для каждого утверждения:

- если исправление требуется — укажи целевой раздел, готовую новую формулировку и идентификатор проверки, которая её обосновывает;
- если утверждение подтверждено — напиши «Изменение не требуется»;
- если это допустимое архитектурное предложение — отдели его от обязательных требований CASE.md.

Не добавляй неподтверждённые требования и новые подсистемы. Не переписывай правильные положения только ради изменений.

Верни наблюдаемые результаты всех четырёх этапов: исходные цитаты, вопросы, ответы с evidence, сопоставление и исправленный текст. Скрытые рассуждения не нужны.

Это проверка документации. Не утверждай, что приложение протестировано, ADR изменён или проведено независимое ревью другой команды.

## Вопросы проверки и evidence

| Вопрос | Источник или проверка | Результат |
|---|---|---|
| В1 (к У1). Какие требования API-1 задают обработку diff: максимальную длину и HTTP-статус при превышении? Есть ли требование по коду при отсутствии поля `diff`? | Ответ: Максимальная длина — 20 000 символов; при превышении — HTTP 413. Источник не задаёт код при отсутствии `diff`. Правило: API-1. Цитата: «`API-1`: diff длиннее 20 000 символов отклоняется с HTTP 413.» Ссылка: [CASE — Правила репозитория](../../practice_01/CASE.md#правила-репозитория). | Итог: подтверждено частично. Обоснование: часть про 413 при `>20000` совпадает с API-1; часть про 422 при отсутствии `diff` не установлена источником (остается архитектурным решением автора ADR). |
| В2 (к У2). Какие категории секретов требуется удалять перед отправкой diff во внешний LLM согласно SEC-1? Предписана ли конкретная форма замены (например, `[REDACTED]`)? | Ответ: Требуется удалять токены, пароли и приватные ключи. Форма замены не задана. Правило: SEC-1. Цитата: «`SEC-1`: перед отправкой во внешний LLM из diff удаляются токены, пароли и приватные ключи.» Ссылка: [CASE — Правила репозитория](../../practice_01/CASE.md#правила-репозитория). | Итог: подтверждено частично. Обоснование: ADR охватывает токены и ключи, но не упоминает пароли; указание «`[REDACTED]`» — допустимая реализация, не требование CASE. |
| В3 (к У3). Для вызова внешнего LLM какое значение таймаута предписано и что должно произойти при ошибке/таймауте согласно REL-1? | Ответ: Таймаут 10 секунд; ошибка превращается в контролируемый ответ. Правило: REL-1. Цитата: «`REL-1`: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.» Ссылка: [CASE — Правила репозитория](../../practice_01/CASE.md#правила-репозитория). | Итог: подтверждено. Обоснование: формулировка ADR полностью соответствует REL-1. |
| В4 (к У4). Какие поля и ограничения структуры ответа задаёт OUT-1 и какие условия включения рисков предписывает QA-1? | Ответ: Ответ содержит `summary`, массив `risks` и массив `checks`; в `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`. Риск включается только при подтверждении строкой diff или правилом репозитория. Правила: OUT-1, QA-1. Цитаты: «`OUT-1`: ответ содержит `summary`, массив `risks` и массив `checks`. В `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`.»; «`QA-1`: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.» Ссылка: [CASE — Правила репозитория](../../practice_01/CASE.md#правила-репозитория). | Итог: подтверждено. Обоснование: ADR отражает и структуру OUT-1, и правило включения рисков из QA-1. |
| В5 (к У5). Что предписывает OBS-1 логировать и что запрещено логировать? | Ответ: В лог пишутся только `request_id`, длительность и статус; содержимое diff и ответа модели не логируется. Правило: OBS-1. Цитата: «`OBS-1`: в лог пишутся только `request_id`, длительность и статус. Содержимое diff и ответа модели не логируется.» Ссылка: [CASE — Правила репозитория](../../practice_01/CASE.md#правила-репозитория). | Итог: подтверждено. Обоснование: формулировка ADR совпадает с OBS-1. |

## Исправленный результат

Для каждого утверждения приведены минимальные корректировки текста ADR или отметка об отсутствии необходимости изменений. Целевой раздел: [ADR — Решение](../../practice_01/adr.md#решение).

- У1 → Предложение правки (API-1): «На уровне API — 413 при `len(diff) > 20000` (API-1). Обработка отсутствия `diff` (422) — внутреннее решение, не требование CASE.» [В1]
- У2 → Предложение правки (SEC-1): «Перед LLM — модуль редактирования секретов, удаляющий из diff токены, пароли и приватные ключи; допускается замена на `[REDACTED]` как реализация (SEC-1).» [В2]
- У3 → Изменение не требуется. [В3]
- У4 → Изменение не требуется. [В4]
- У5 → Изменение не требуется. [В5]
