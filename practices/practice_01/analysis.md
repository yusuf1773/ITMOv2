# Анализ процесса: AS IS и TO BE

## AS IS

Событие: разработчик отправляет HTTP-запрос `POST /api/reviews` с телом `{ "diff": "..." }`.

Процесс сейчас:
- FastAPI-эндпойнт без валидации извлекает `payload["diff"]` и передаёт в `ReviewService.review`.
- `ReviewService` синхронно формирует строковый prompt и вызывает внешний LLM без таймаута и редактирования секретов.
- Ответ LLM возвращается как `{ "comment": answer }` без структуры OUT-1.

Участники: автор PR/ревьюер (запрос), API слоя, ReviewService, внешний LLM, человек-ревьюер (читает ответ).

Задержки и риски: блокировка при долгом LLM-ответе (нет REL-1), 500 при отсутствии поля `diff` (KeyError), отсутствие ограничения размера diff (нет API-1), возможная утечка секретов (нет SEC-1), слабая пригодность ответа (нет OUT-1).


## TO BE

Целевой компактный процесс для одного вызова API соответствует правилам CASE.md.

```mermaid
flowchart LR
    A[POST /api/reviews с diff] --> V{Валидация тела}
    V -- нет diff --> E422[Ошибка 422]
    V -- diff > 20k --> E413[Ошибка 413]
    V -- ок --> R[Редактор секретов (SEC-1)]
    R --> P[Формирование prompt]
    P --> T{LLM с timeout 10s (REL-1)}
    T -- timeout/исключение --> CERR[Контролируемый ответ]
    T -- успех --> A1[Парсинг ответа]
    CERR --> O[OUT-1: summary, risks<=3, checks]
    A1 --> O
    O --> H[Проверка человеком]
```

## Разница

| Что меняется | AS IS | TO BE | Как проверим изменение |
|---|---|---|---|
| Валидация тела | Нет, KeyError -> 500 | Явная схема/проверка, 422 | E2E-запрос без `diff` даёт 422 |
| Ограничение размера | Нет | 413 при >20 000 символов | Нагрузочный тест длинного diff |
| Редактирование секретов | Нет | Редактор заменяет секреты на [REDACTED] | Интеграционный тест с токеном в diff |
| Таймаут LLM | Нет | 10s timeout с контролируемым ответом | Интеграционный тест с «зависшей» заглушкой |
| Формат ответа | `{comment: str}` | OUT-1: `summary`, `risks` (<=3), `checks` | Unit/интеграционные проверки структуры |

## Как использовали AI

- Для чего: структурировать процесс AS IS и спроектировать минимальный TO BE под правила CASE.md, сохранив границы SCOPE-1.
- Тип промпта: master prompt (структура, без генерации кода).
- Строка в [`prompts.md`](prompts.md): P1-02 (Master Prompt v1).
- Что проверили и исправили сами: сверили каждый узел диаграммы с пунктами CASE.md (SEC-1, API-1, REL-1, OUT-1) и с TRAINING_PR.diff; исключили неподтверждённые шаги.
