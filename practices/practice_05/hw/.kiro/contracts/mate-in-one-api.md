# Общий контракт API: «Мат в один ход»

## Статус и область действия

Статус: **УТВЕРЖДЁН пользователем 28 октября 2026 года** на основании итогового предложения backend и уточнений, принятых UI-командой.

Этот документ содержит полный согласованный контракт взаимодействия UI и backend для mate-in-one-backend. Он фиксирует форматы, поведение и границы интеграции. Утверждение контракта не означает утверждения всех требований, дизайна или задач реализации. Создание документа не разрешает создание исходников приложения. Ранее сохранённые версии в before-agreement остаются независимым снимком до согласования.

Уточнения пользователя имеют приоритет над предыдущими предложениями:
- порядок проверки: маршрут и метод → доступность набора → существование ID → Content-Type → JSON → структура и типы → формат хода → шахматная проверка;
- PROMOTION_REQUIRED открывает выбор из details.choices;
- окончание каталога определяется UI по нажатию «Следующая задача» на последней задаче;
- UI и API обслуживаются Flask с одного origin; клиент использует относительный /api/v1.

## 1. Границы и основные правила

Backend на Python и Flask с python-chess хранит ровно пять задач в локальном JSON. Каждая задача имеет уникальный непустой строковый идентификатор и исходный FEN. Порядок каталога стабилен для неизменного набора.

Backend определяет допустимость хода и мат. UI отображает позицию, принимает выбор клеток и фигуры превращения и показывает серверный результат. UI не вычисляет шахматную допустимость, необходимость превращения или наличие мата.

Нет БД, регистрации, авторизации, Stockfish, серверных пользовательских сессий, истории попыток и генерации задач. Полноценная партия и выдача списка допустимых ходов для подсветки не входят в контракт. Решения и перечень матующих ходов не выдаются.

Каждая попытка оценивается относительно исходной позиции задачи, независимо от предшествующих попыток и других клиентов. Серверная позиция задачи не меняется. При нескольких допустимых матующих ходах принимается каждый.

## 2. Размещение и общие форматы

UI и API доступны через один origin Flask. Origin — сочетание схемы, хоста и порта. Клиент использует относительный префикс /api/v1. Пример размещения, а не обязательный адрес:

```text
http://127.0.0.1:5000/
http://127.0.0.1:5000/api/v1/tasks
```

В утверждённой схеме отдельная настройка CORS не требуется. Разные origins, списки разрешённых origins и специальные CORS-правила в этот контракт не включены; изменение размещения требует отдельного согласования. UI не открывается через file://. Cookies и передача учётных данных для работы тренажёра не нужны.

Прикладные ответы API имеют Content-Type application/json. POST попытки использует Content-Type application/json. Ответы ошибок приложения также имеют JSON-формат. При отсутствии соединения, остановленном процессе или ошибке инфраструктуры наличие JSON-ответа не гарантируется; UI обрабатывает такие случаи отдельно.

Идентификатор задачи — непустая строка; ID передаётся в маршруте, а не в теле попытки. UI использует ID, полученные из каталога. Примеры task-01 … task-05 иллюстративны и не закрепляют конкретные значения.

## 3. Маршруты

| Метод | Маршрут | Назначение | Успех |
| --- | --- | --- | --- |
| GET | /api/v1/tasks | Упорядоченный каталог | 200, объект tasks |
| GET | /api/v1/tasks/{task_id} | Исходная позиция выбранной задачи | 200, объект id и fen |
| POST | /api/v1/tasks/{task_id}/attempts | Проверка одной попытки | 200, шахматный результат; либо ошибка из раздела 8 |

Отдельных маршрутов /next, завершения набора, пользовательского прогресса и серверного курсора нет.

## 4. Каталог и исходная позиция

### 4.1. Каталог

GET /api/v1/tasks возвращает HTTP 200:

```json
{
  "tasks": [
    {"id": "task-01"},
    {"id": "task-02"},
    {"id": "task-03"},
    {"id": "task-04"},
    {"id": "task-05"}
  ]
}
```

Схема ответа (JSON Schema 2020-12):

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["tasks"],
  "additionalProperties": false,
  "properties": {
    "tasks": {
      "type": "array", "minItems": 5, "maxItems": 5, "uniqueItems": true,
      "items": {
        "type": "object", "required": ["id"], "additionalProperties": false,
        "properties": {"id": {"type": "string", "minLength": 1}}
      }
    }
  }
}
```

### 4.2. Позиция

GET /api/v1/tasks/task-01 возвращает HTTP 200, например:

```json
{"id":"task-01","fen":"7k/8/5KQ1/8/8/8/8/8 w - - 0 1"}
```

Схема ответа:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object", "required": ["id", "fen"], "additionalProperties": false,
  "properties": {
    "id": {"type": "string", "minLength": 1},
    "fen": {"type": "string", "minLength": 1}
  }
}
```

FEN содержит все шесть полей, включая очередь хода, права рокировки и поле взятия на проходе. Его шахматная валидность — обязательное семантическое условие сверх проверки схемы. Возвращаемый id совпадает с запрошенным.

UI извлекает расстановку и сторону хода для отображения. Белые располагаются снизу независимо от очереди хода. UI показывает ID задачи и постоянный текст «Мат в один ход»; отдельные title и поле стороны хода не передаются.

Приведённая позиция иллюстрирует формат и не определяет обязательный состав учебного набора.

## 5. Формат попытки

POST /api/v1/tasks/{task_id}/attempts принимает JSON-объект ровно с тремя обязательными полями:

```json
{"from":"g6","to":"g7","promotion":null}
```

Схема тела:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["from", "to", "promotion"],
  "additionalProperties": false,
  "properties": {
    "from": {"type": "string", "pattern": "^[a-h][1-8]$"},
    "to": {"type": "string", "pattern": "^[a-h][1-8]$"},
    "promotion": {"enum": [null, "q", "r", "b", "n"]}
  }
}
```

Координаты и обозначения фигур принимаются в нижнем регистре. q — ферзь, r — ладья, b — слон, n — конь; null означает, что фигура превращения не выбрана.

Схема задаёт допустимое тело; точная категория нарушения определяется поэтапно:
- не JSON-объект, отсутствие поля, лишнее поле или неверный тип: 400 INVALID_REQUEST;
- from/to должны быть строками; promotion должен быть null либо строкой;
- строка координаты вне a1–h8 или неизвестная строка promotion: 400 INVALID_MOVE_FORMAT;
- корректно записанный, но невозможный ход: HTTP 200 с illegal;
- одинаковые from/to не обозначают пропуск хода и дают illegal;
- указание фигуры превращения для хода, в котором превращение невозможно, даёт illegal.

Не передаются task_id, собственный FEN, UCI или другие поля в теле. Источник позиции — серверный набор задач.

Рокировка описывается перемещением короля с исходной на конечную клетку. Взятие на проходе — перемещением пешки с исходной на конечную клетку. Специальные права и очередь хода берутся из исходного FEN.

## 6. Выбор фигуры превращения

Шахматная проверка выполняется после проверок запроса в порядке раздела 8.3. Отсутствие допустимого превращения само по себе не означает illegal: обычный допустимый ход не требует превращения.

### 6.1. Если promotion равен null

1. Сервер сначала проверяет обычный ход между выбранными клетками без превращения. Если он допустим, возвращается HTTP 200 с correct при мате либо incorrect при отсутствии мата, а также fen_after по разделу 7. Выбор фигуры не запрашивается.
2. Только если обычный ход недопустим, сервер проверяет, существует ли между теми же клетками допустимый ход с превращением пешки.
3. Если допустимое превращение существует, сервер отвечает HTTP 400:

```json
{
  "error": {
    "code": "PROMOTION_REQUIRED",
    "message": "Выберите фигуру превращения",
    "details": {"choices": ["q", "r", "b", "n"]}
  }
}
```

4. Если нет ни допустимого обычного хода, ни допустимого превращения между выбранными клетками, возвращается HTTP 200 с illegal и fen_after: null. Невозможный ход не запускает диалог выбора даже при геометрическом перемещении пешки на последнюю горизонталь.

### 6.2. Если фигура указана явно

При promotion, равном q, r, b или n, сервер проверяет именно конкретный ход с указанной фигурой. Допустимый ход даёт correct или incorrect в зависимости от наличия мата; недопустимый — illegal. Подмена фигуры, повторная проверка другого превращения вместо выбранного и автоматическая подстановка ферзя не выполняются.

### 6.3. Выбор в UI

UI строит выбор фигуры по details.choices из ответа PROMOTION_REQUIRED. После выбора UI отправляет запрос для той же задачи и клеток с выбранным promotion. Автоматического выбора ферзя нет.

PROMOTION_REQUIRED — промежуточный ответ уточнения, без шахматного результата и изменения позиции. Серверное состояние выбора не сохраняется. Запрос с выбранной фигурой является новой независимой попыткой относительно исходной позиции задачи.

## 7. Шахматные результаты

Все три результата возвращаются с HTTP 200:

| result | Значение | fen_after | Действие UI |
| --- | --- | --- | --- |
| correct | Допустимый ход поставил мат | Полный FEN после хода | Показать успех и серверную позицию; локально заблокировать новые попытки этой задачи |
| incorrect | Допустимый ход не поставил мат | Полный FEN после хода | Показать неудачу; сохранить исходную доску для следующей попытки |
| illegal | Корректно описанный ход недопустим | null | Показать недопустимость; сохранить исходную доску |

Пример правильного хода из позиции раздела 4:

```json
{"task_id":"task-01","result":"correct","fen_after":"7k/6Q1/5K2/8/8/8/8/8 b - - 1 1"}
```

Пример недопустимого хода:

```json
{"task_id":"task-01","result":"illegal","fen_after":null}
```

Схема результата:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["task_id", "result", "fen_after"],
  "additionalProperties": false,
  "properties": {
    "task_id": {"type": "string", "minLength": 1},
    "result": {"enum": ["correct", "incorrect", "illegal"]},
    "fen_after": {"type": ["string", "null"]}
  },
  "oneOf": [
    {"properties": {"result": {"enum": ["correct", "incorrect"]}, "fen_after": {"type": "string", "minLength": 1}}},
    {"properties": {"result": {"const": "illegal"}, "fen_after": {"type": "null"}}}
  ]
}
```

Шах без мата и пат дают incorrect. Мат означает, что после допустимого хода король противоположной стороны находится под шахом и у этой стороны нет допустимых ходов. Пустая исходная клетка, чужая фигура и оставление своего короля под шахом дают illegal. Любой допустимый матующий ход принимается независимо от наличия других решений.

task_id совпадает с ID в маршруте. fen_after для допустимого хода соответствует именно его применению к исходной позиции. Наличие fen_after не меняет исходную задачу и не создаёт продолжение партии.

## 8. Ошибки и порядок проверок

### 8.1. Общая форма

```json
{
  "error": {
    "code": "TASK_NOT_FOUND",
    "message": "Задача не найдена",
    "details": {}
  }
}
```

В ошибочном ответе нет result и fen_after. code — стабильная машинная категория; UI принимает решения по нему. message — пояснение на русском языке, его точный текст не используется как машинный признак. details всегда является объектом, обычно пустым; для PROMOTION_REQUIRED содержит choices.

Схема ошибки:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object", "required": ["error"], "additionalProperties": false,
  "properties": {
    "error": {
      "type": "object", "required": ["code", "message", "details"], "additionalProperties": false,
      "properties": {
        "code": {"enum": ["INVALID_JSON", "INVALID_REQUEST", "INVALID_MOVE_FORMAT", "PROMOTION_REQUIRED", "TASK_NOT_FOUND", "ROUTE_NOT_FOUND", "METHOD_NOT_ALLOWED", "UNSUPPORTED_MEDIA_TYPE", "INTERNAL_ERROR", "SERVICE_UNAVAILABLE"]},
        "message": {"type": "string", "minLength": 1},
        "details": {"type": "object"}
      },
      "if": {"properties": {"code": {"const": "PROMOTION_REQUIRED"}}},
      "then": {
        "properties": {
          "details": {
            "type": "object", "required": ["choices"], "additionalProperties": false,
            "properties": {"choices": {"const": ["q", "r", "b", "n"]}}
          }
        }
      },
      "else": {"properties": {"details": {"maxProperties": 0}}}
    }
  }
}
```

### 8.2. Коды и статусы

| HTTP | code | Условие |
| --- | --- | --- |
| 400 | INVALID_JSON | Тело не разбирается как JSON |
| 400 | INVALID_REQUEST | Неверная структура, отсутствующие или лишние поля, неверные типы |
| 400 | INVALID_MOVE_FORMAT | Неверная запись координат либо неизвестная строка promotion |
| 400 | PROMOTION_REQUIRED | Для допустимого перемещения необходимо выбрать фигуру превращения |
| 404 | TASK_NOT_FOUND | Набор доступен, но запрошенного ID нет |
| 404 | ROUTE_NOT_FOUND | Маршрут API отсутствует |
| 405 | METHOD_NOT_ALLOWED | Маршрут существует, но метод не поддерживается |
| 415 | UNSUPPORTED_MEDIA_TYPE | Неподдерживаемый Content-Type запроса попытки |
| 500 | INTERNAL_ERROR | Непредвиденная внутренняя ошибка, без трассировки клиенту |
| 503 | SERVICE_UNAVAILABLE | HTTP-сервис работает, но набор задач недоступен или не готов к использованию |

### 8.3. Приоритет

Для запроса попытки действует следующий порядок; первая выявленная ошибка определяет ответ:

1. Маршрут и метод: ROUTE_NOT_FOUND либо METHOD_NOT_ALLOWED.
2. Доступность набора: SERVICE_UNAVAILABLE.
3. Существование ID: TASK_NOT_FOUND.
4. Content-Type: UNSUPPORTED_MEDIA_TYPE.
5. Разбор JSON: INVALID_JSON.
6. Структура и типы: INVALID_REQUEST.
7. Формат хода: INVALID_MOVE_FORMAT.
8. Шахматная проверка: PROMOTION_REQUIRED при условиях раздела 6 либо один из трёх шахматных результатов.

Для GET применяются релевантные шаги: маршрут/метод, доступность набора и, при запросе позиции, существование ID. Неизвестный ID с повреждённым телом даёт TASK_NOT_FOUND, если набор доступен. При недоступном наборе существование ID не проверяется: возвращается SERVICE_UNAVAILABLE.

### 8.4. Готовность набора

До обслуживания запросов задач проверяются: читаемость и структура локального JSON, ровно пять задач, уникальные непустые строковые ID, наличие FEN, синтаксическая и шахматная допустимость позиций. Каждая позиция не завершена и имеет хотя бы один допустимый матующий ход.

При непригодном наборе оператор получает сообщение об ошибке, а выдача задач и проверка попыток не выполняются. Если HTTP-сервис остаётся доступен, соответствующие запросы получают 503. Если процесс не запущен, клиент обрабатывает отсутствие соединения; искусственный HTTP-ответ не предполагается.

## 9. Навигация и окончание каталога

1. UI получает каталог и загружает исходную позицию первого элемента.
2. «Следующая задача» доступна независимо от решения текущей задачи: пропуск разрешён.
3. UI выбирает следующий ID по порядку массива. Текущая задача меняется только после успешной загрузки целевой позиции.
4. При ошибке загрузки целевая задача не считается открытой; повтор выполняет запрос того же ID без дополнительного продвижения.
5. Само открытие последней задачи не завершает набор и не блокирует её решение.
6. По нажатию «Следующая задача» на последней задаче UI определяет отсутствие следующего элемента, показывает «Задачи закончились» и завершает просмотр и попытки этого прохождения. Запрос несуществующей следующей задачи не отправляется.
7. Сообщение об окончании не означает, что все задачи решены: пропуски разрешены.

UI проходит фактически полученный каталог без числа 5 в логике навигации. Обязательство backend выдать ровно пять задач при этом сохраняется. Отдельного серверного сообщения о завершении, статуса прохождения и серверного курсора нет. 404 означает ошибку обращения, а не конец набора.

## 10. Тайм-аут, повторы и устаревшие ответы

- UI отводит на один запрос 10 секунд, включая получение ответа. Это предел ожидания UI, а не обещание производительности backend.
- По истечении срока UI прекращает ожидание, снимает блокировку действий и предлагает ручной повтор. Отмена ожидания не подтверждает остановку обработки сервером.
- Автоматических повторов нет. При сетевом сбое, тайм-ауте или 5xx пользователь может вручную повторить тот же запрос.
- Повтор сохраняет метод, целевой ID и тело. При повторе загрузки следующей задачи не происходит дополнительного перехода вперёд.
- PROMOTION_REQUIRED запускает выбор из details.choices; последующий запрос с выбранной фигурой является уточнённой попыткой, а не повтором неизменённого тела.
- Остальные 4xx требуют исправления обращения и не запускают бесконечные повторы.
- Пока запрос выполняется, повторные конфликтующие действия заблокированы. После завершения, ошибки или тайм-аута временная блокировка снимается; блокировка новых попыток после correct сохраняется по правилам раздела 7.
- Ответ устаревшего запроса не меняет актуальный экран. UI различает отдельные запросы локально, включая разные попытки одной задачи; одного task_id для этого недостаточно.
- При неизменном наборе одинаковая попытка даёт одинаковую шахматную оценку. Повторы не создают историю и не изменяют позиции; отдельный ключ идемпотентности не требуется.
- Неожиданный формат ответа UI показывает как ошибку обмена, сохраняя возможность повторить действие. Сетевые ошибки и локальные тайм-ауты не выдаются за correct, incorrect или illegal.

## 11. Проверяемые сценарии контракта

- Каталог содержит пять уникальных ID в стабильном порядке; позиция содержит исходный FEN.
- Допустимый матующий ход → 200 correct и FEN после хода.
- Допустимый ход без мата, включая шах и пат → 200 incorrect и FEN после хода.
- Невозможный корректно записанный ход → 200 illegal и null.
- Допустимое превращение без выбора → 400 PROMOTION_REQUIRED; UI использует details.choices и отправляет уточнённую попытку.
- Невозможное перемещение с предполагаемым превращением → illegal без диалога выбора.
- Недоступный набор имеет приоритет над неизвестным ID; неизвестный ID имеет приоритет над неверным Content-Type и повреждённым JSON.
- Последняя задача остаётся решаемой до успеха либо явного перехода; нажатие «Следующая задача» завершает каталог локально.
- Повтор после тайм-аута не меняет исходную позицию; запоздавший ответ не заменяет новый экран.
- UI и API работают с одного origin, запросы используют относительный /api/v1.
