# Практика 7.2. Поддержка пользователей с помощью AI

Репозиторий — [yusuf1773/emulators_manager](https://github.com/yusuf1773/emulators_manager). Тестовые обращения доступны в разделе [GitHub Issues](https://github.com/yusuf1773/emulators_manager/issues).

В работе реализованы обработка новых Issues в n8n и отправка еженедельной статистики по почте. В задании со звёздочкой письмо дополнено сравнением с сохранённой сводкой и комментарием модели.

## Часть 1. Автоматическая обработка обращений

Схемы — [основной workflow](workflows/WF1-main.json) и [классификатор](workflows/WF1-classifier.json).

1. **Приём события.** GitHub Trigger получает событие Issues. Фильтр пропускает действие `opened`. Нода «Issue ещё не обработан» проверяет наличие глобального `issue.id` в Data Table `processed_issues`. Если запись уже есть, дальнейшая обработка прекращается.
2. **Классификация.** Отдельный workflow получает `title` и `body`. Модель `openai/gpt-5.2` оценивает обращение по определениям и примерам из промпта. Structured Output Parser проверяет, что ответ содержит допустимый `type` и числовой `confidence` от 0 до 1.
3. **Маршрутизация.** Для `bug`, `task` и `feature` при уверенности от 0.8 используется соответствующая ветка Switch. В остальных случаях выбирается `unknown`. Ноды GitHub API применяют действие к `issue.number` в нужном репозитории.
4. **Приветствие и сохранение.** При `author_association = NONE` workflow добавляет `first-time-contributor` и публикует приветствие. В конце сохраняются `issue_id`, автор и время создания обращения.

| Маршрут | Метка | Ответ по типу |
| --- | --- | --- |
| `bug` | `bug` | Просьба уточнить шаги воспроизведения, поведение и версии |
| `task` | `task` | Шаблонный ответ на вопрос или задачу |
| `feature` | `feature-request` | Шаблонный ответ на предложение |
| `unknown` | `needs-triage` | Шаблонный ответ по типу пропускается |

## Часть 2. Недельный HTML-отчёт

| Workflow | Назначение |
| --- | --- |
| [Планировщик](workflows/WF2-report-scheduler.json) | Запускается по понедельникам в 09:00 по Москве по правилу `0 9 * * MON`. Передаёт владельца, репозиторий и адрес получателя. |
| [Формирование и отправка](workflows/WF2-weekly-report-star.json) | Проверяет параметры, вызывает сбор статистики, формирует HTML и отправляет письмо через Gmail. В этой версии включена звёздочка. |
| [Сбор статистики](workflows/WF2-weekly-statistics.json) | Проверяет репозиторий и собирает данные GitHub за последние 168 часов. Возвращает период, счётчики и строки таблицы. |

Сборщик использует четыре поиска GitHub API. Он считает созданные обращения по `created_at`, закрытые по `closed_at`, обновлённые по `updated_at` и отдельно новые обращения с меткой `needs-triage`. Ноды собирают страницы ответов и проверяют полноту результатов. Новые обращения группируются по паре «тип + автор». Счётчик «Создано» и таблица строятся из одного набора.

## Задание со звёздочкой. Сравнение сводок

Сводка сохраняется в `weekly_issue_reports`. Ключ состоит из репозитория и даты понедельника недели, в которую заканчивается отчётный период. При повторном последовательном запуске за ту же неделю операция upsert обновляет строку. Для сравнения workflow ищет ключ предыдущей недели и вычисляет разницу в JavaScript. Если записи нет, письмо сообщает, что сравнение недоступно.

Модель `openai/gpt-5` получает текущие и предыдущие показатели и готовую разницу. Её ответ добавляется в письмо как «AI-комментарий недели».

На [скриншоте сравнения](screenshots/wf2-star-comparison.png) для текущего отчёта найдена сохранённая сводка с `week_key = 2026-11-16`.

| Показатель | Сохранённая сводка | Текущий отчёт | Разница |
| --- | ---: | ---: | ---: |
| Создано | 3 | 4 | +1 |
| Закрыто | 0 | 0 | 0 |
| Обновлено | 3 | 4 | +1 |
| Новые с `needs-triage` | 0 | 1 | +1 |

В [письме](screenshots/wf2-star-email.png) видны все четыре изменения и комментарий модели. Предыдущая сводка была собрана 21 ноября, текущая — 23 ноября. Оба окна содержат последние 168 часов на момент сбора, поэтому в показанном запуске они пересекаются. Разница рассчитана между сохранёнными сводками.

## Импорт схем в n8n

Импортируйте классификатор перед WF1. Для отчёта сначала импортируйте сбор статистики, затем формирование письма и планировщик. В нодах Execute Workflow заново выберите соответствующие импортированные workflow, поскольку ссылки содержат идентификаторы исходного экземпляра n8n. Назначьте credentials GitHub, OpenAI и Gmail, укажите получателя письма и проверьте часовой пояс планировщика.

Для запуска нужны Data Tables `processed_issues` (`issue_id` — число, `author` — строка, `created_at` — дата) и `weekly_issue_reports` (`repository`, `week_key` — строки, `period_from`, `period_to` — даты, `created`, `closed`, `updated`, `needs_triage` — числа).
