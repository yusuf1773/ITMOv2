- Что хотим улучшить: конкретность проверки главного риска

## Примеры

### Хороший результат

Исходная формулировка:
«Проверим ограничение размера diff». 

Улучшенная формулировка:
«Тестовые данные: diff длиной 20 001 символ.
Действие: отправить запрос с этим diff.
Ожидаемый результат: HTTP 413».

Почему хорошо: определены тестовые данные, действие и наблюдаемый результат.

Исходная формулировка:
«Проверим формат ответа».

Улучшенная формулировка:
«Тестовые данные: допустимый diff без секретов и заглушка LLM, возвращающая корректный результат ревью.
Действие: отправить запрос и изучить JSON-ответ сервиса.
Ожидаемый результат: присутствуют summary, массив risks и массив checks; в risks не больше трёх элементов, каждый содержит file, line, evidence и risk».

Почему хорошо: перечислены условия проверки и признаки успешного результата.

### Плохой результат

«Провести качественное тестирование безопасности и убедиться, что всё работает».

Почему плохо: отсутствуют конкретные данные, действия и ожидаемый результат.

## Запрос

Улучши формулировку проверки главного риска в practices/practice_01/adr.md. Используй фактический текст ADR и правило SEC-1 из practices/practice_01/CASE.md.

Задача касается содержания документа: нужно предложить понятные проверки, а не реализовать сервис или выполнить тесты.

Используй два хороших примера ниже как образцы преобразования общей формулировки в конкретную. Перенеси их структуру на задачу маскирования секретов, не копируя предметное содержание.

Хороший пример 1

Исходная формулировка:
«Проверим ограничение размера diff».

Улучшенная формулировка:
«Тестовые данные: diff длиной 20 001 символ.
Действие: отправить запрос с этим diff.
Ожидаемый результат: HTTP 413».

Почему хорошо: определены тестовые данные, действие и наблюдаемый результат.

Хороший пример 2

Исходная формулировка:
«Проверим формат ответа».

Улучшенная формулировка:
«Тестовые данные: допустимый diff без секретов и заглушка LLM, возвращающая корректный результат ревью.
Действие: отправить запрос и изучить JSON-ответ сервиса.
Ожидаемый результат: присутствуют summary, массив risks и массив checks; в risks не больше трёх элементов, каждый содержит file, line, evidence и risk».

Почему хорошо: перечислены условия проверки и признаки успешного результата.

Плохой пример

«Провести качественное тестирование безопасности и убедиться, что всё работает».

Почему плохо: отсутствуют конкретные данные, действия и ожидаемый результат.

Теперь обработай пункт «Как проверим риск» из раздела «Последствия и главный риск» текущего ADR.

Верни:
1. Дословную исходную формулировку этого пункта.
2. Три предложенные проверки: отдельно для токенов, паролей и приватных ключей.
3. Краткую формулировку для замены пункта в ADR.
4. Краткое объяснение, что стало конкретнее благодаря примерам.

Для каждой проверки используй структуру:
- Тестовые данные.
- Действие.
- Ожидаемый результат.

Используй только синтетические секреты. Для приватного ключа допустимо описать тестовый PEM-блок без генерации настоящего ключа.

Действие должно позволять перехватить prompt перед отправкой во внешний LLM. Ожидаемый результат — отсутствие исходного значения секрета в этом prompt.

Если ADR предусматривает замену на [REDACTED], укажи это как решение ADR. Не приписывай этот конкретный способ замены правилу SEC-1.

Не добавляй требования сохранять кавычки, PEM-маркеры или структуру diff. Не расширяй эксперимент проверками логирования.

Не утверждай, что тесты выполнены. Отметь, что предложенные проверки известных примеров не гарантируют обнаружение секретов любых форматов.

Если исходная формулировка уже конкретна, честно оцени её и предложи только обоснованные улучшения.

## Что получили

Исходная формулировка пункта «Как проверим риск» из ADR:
«Интеграционные тесты с различными шаблонами секретов; периодический review шаблонов редактирования.»

Предложенные проверки SEC-1 с перехватом prompt перед внешним LLM:

1) Токены
- Тестовые данные: учебный diff с синтетическим токеном вида test_token_ABC123456789, встроенным в строку изменения.
- Действие: отправить запрос к сервису и перехватить сформированный prompt в точке перед внешним LLM (мок транспортного слоя/хук на этапе подготовки prompt).
- Ожидаемый результат: в перехваченном prompt отсутствует исходное значение токена; согласно решению ADR, вместо него присутствует нейтральная маскировка [REDACTED].

2) Пароли
- Тестовые данные: учебный diff с синтетическим паролем, например password: P@ssw0rd_test_! в добавленной строке конфигурации.
- Действие: отправить запрос и перехватить prompt до внешнего LLM тем же способом.
- Ожидаемый результат: исходное значение пароля отсутствует в prompt; решение ADR предусматривает замену чувствительного фрагмента на [REDACTED].

3) Приватные ключи
- Тестовые данные: учебный diff с синтетическим блоком приватного ключа (невалидный демонстрационный PEM-блок, включённый в diff для проверки маскирования).
- Действие: отправить запрос и перехватить prompt непосредственно перед отправкой во внешний LLM.
- Ожидаемый результат: исходные строки приватного ключа отсутствуют в перехваченном prompt; по решению ADR чувствительный фрагмент заменён на [REDACTED].

Предложение для ADR (краткая замена пункта «Как проверим риск»):
«SEC-1: три интеграционные проверки с перехватом prompt перед внешним LLM — для токенов, паролей и приватных ключей; ожидаемый результат — отсутствие исходных значений в prompt (в решении ADR — замена на [REDACTED]).»

Что стало конкретнее: сформулированы тестовые данные, точка действия (перехват prompt перед LLM) и наблюдаемый результат для трёх типов секретов; при этом отмечено, что эти примеры не гарантируют обнаружение секретов любых форматов.
