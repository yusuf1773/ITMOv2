- Обработка timeout или исключения внешнего LLM в первом сценарии ADR.
- Критерии выбора:
  - Обязательные (CASE):
    - «REL-1: внешний LLM-вызов имеет timeout 10 секунд; ошибка превращается в контролируемый ответ.» — см. [CASE — Правила репозитория](../../practice_01/CASE.md#правила-репозитория)
    - «OUT-1: ответ содержит `summary`, массив `risks` и массив `checks`. В `risks` максимум три элемента с полями `file`, `line`, `evidence`, `risk`.» — см. [CASE — Правила репозитория](../../practice_01/CASE.md#правила-репозитория)
    - «QA-1: риск включается в ответ, только если он подтверждён строкой diff или правилом репозитория.» — см. [CASE — Правила репозитория](../../practice_01/CASE.md#правила-репозитория)
    - «SCOPE-1: сервис только советует; он не пишет код и не выполняет действия в GitHub.» — см. [CASE — Правила репозитория](../../practice_01/CASE.md#правила-репозитория)
    - Отсутствие неподтверждённых выводов о рисках (следствие QA-1).
  - Предпочтительные:
    - минимальная сложность решения;
    - понятное сообщение пользователю о результате обработки;
    - отсутствие лишних внешних вызовов;
    - возможность описать воспроизводимую проверку.
  - Ограничения сценария из ADR: «Возможен рост латентности из-за редактирования и валидаций; ограничение размера diff.» — см. [ADR — Решение](../../practice_01/adr.md#решение) и раздел «Последствия и главный риск» исходного ADR.

## Запрос

Примени Tree of Thoughts с BFS и backtracking для выбора способа обработки ошибки внешнего LLM в первом сценарии ADR.

Источники:
- practices/practice_01/adr.md — существующее решение;
- practices/practice_01/CASE.md — требования.

Задача: сравнить варианты поведения при timeout или исключении LLM и подготовить предложение для ADR. Сам ADR изменять нельзя.

Показывай только краткие описания вариантов, критерии, результаты проверок, порядок обхода и основания выбора. Скрытые внутренние рассуждения не нужны.

### Требования и критерии

Сначала извлеки применимые требования из CASE.md с точными цитатами и ссылками. Отдельно укажи ограничения выбранного сценария ADR.

Обязательные критерии:
- соблюдение REL-1;
- соблюдение OUT-1 и QA-1;
- сохранение границ SCOPE-1;
- отсутствие неподтверждённых выводов о рисках.

Критерии предпочтения:
- минимальная сложность;
- понятное сообщение пользователю о результате обработки;
- отсутствие лишних внешних вызовов;
- возможность описать воспроизводимую проверку.

Не превращай критерии предпочтения в требования CASE.md. Например, отсутствие автоматических повторов может быть выбором автора, но не запретом из CASE.md.

### Структура дерева

Корень:
«Как обработать timeout или исключение внешнего LLM?»

Уровень 1 — три альтернативы:
- A: вернуть контролируемый ответ без повторного вызова.
- B: выполнить один автоматический повтор, затем вернуть контролируемый ответ при повторном сбое.
- C: после сбоя сформировать ограниченный результат локальными детерминированными проверками без нового вызова LLM.

Это кандидаты для оценки, а не заранее выбранные решения. Не предполагаи, что один из них обязательно нарушает правила.

### Поиск в ширину — BFS

1. Сначала кратко опиши и оцени ВСЕ три варианта уровня 1.
2. Не переходи к детализации A, пока не рассмотрены B и C.
3. Для каждого варианта, не исключённого обязательными критериями, создай два конкретных подварианта следующего уровня: A1/A2, B1/B2, C1/C2.
4. Подварианты должны различаться существенным решением: например, формой сообщения об ошибке, условиями повтора или границами локальных проверок. Не создавай заведомо нелепые варианты ради их отбрасывания.
5. Рассмотри все созданные узлы уровня 2 перед окончательным выбором.

Зафиксируй краткий порядок обхода, например:
Корень → A → B → C → A1 → A2 → B1 → B2 → C1 → C2.

Покажи фактический порядок. Если ветвь исключена и её потомки не создавались, укажи причину.

Ограничение: максимум 10 узлов, включая корень; глубина — не более двух уровней альтернатив.

Для каждого узла укажи только:
- краткое описание;
- результат проверки обязательных критериев;
- основные плюсы и минусы;
- статус: оставить, исключить или кандидат для выбора;
- ссылку на правило, если оценка основана на CASE.md.

### Проверка кандидата и backtracking

После обхода выбери предварительно лучший конечный вариант по объявленным критериям.

Проверь его на сценариях:
- timeout LLM;
- исключение LLM;
- отсутствие полученного результата ревью;
- риск того, что пустой risks пользователь примет за подтверждение безопасности;
- дополнительные условия, которые предполагает выбранная ветвь.

Это проверка описания решения, а не запуск приложения.

Если обнаружен конкретный недостаток:
1. Зафиксируй, какое условие не выполнено.
2. Вернись к ближайшему узлу с подходящей альтернативой.
3. Рассмотри соседний подвариант; если он не подходит, вернись к другой ветви.
4. Повтори проверку нового кандидата.

Зафиксируй возврат в виде:
«Кандидат → обнаруженная проблема → узел возврата → новая альтернатива → результат проверки».

Допускается не более двух возвратов.

Не придумывай провал ради демонстрации backtracking. Если первый кандидат проходит проверки, напиши:
«Backtracking не потребовался: оснований отклонять кандидата не обнаружено».
В таком случае отдельно укажи условие, при котором понадобился бы возврат, и доступную альтернативную ветвь. Не выдавай этот условный пример за фактически выполненный возврат.

### Итог

Верни:
1. Применимые требования и критерии.
2. Краткую таблицу трёх альтернатив A/B/C.
3. Дерево подвариантов и порядок BFS.
4. Оценки конечных вариантов.
5. Проверку предварительного кандидата.
6. Фактические возвраты либо честную отметку об их отсутствии.
7. Выбранный вариант и готовое предложение для раздела «Решение» ADR.
8. План проверки выбранного поведения: вход или сбой → ожидаемый результат.

Не назначай HTTP-код как якобы обязательный, если CASE.md его не определяет. Не обещай выявление рисков, для которых нет evidence.

Если ни один кандидат не удовлетворяет обязательным условиям, не выбирай заведомо неверный вариант: укажи, какое решение или уточнение требуется от автора ADR.

Не утверждай, что ADR изменён или тесты приложения выполнены.

## Внешне описанные альтернативы

| Альтернатива | Плюсы | Минусы | Оценка по критериям |
|---|---|---|---|
| A | Минимальная сложность; без лишних внешних вызовов; легко проверить | Риск неверной интерпретации пустых `risks` как «безопасно» без явного пояснения | Обязательные: соблюдает REL-1/OUT-1/QA-1/SCOPE-1; Предпочтения: сильная при ясном сообщении |
| B | Шанс получить результат за одну попытку больше | Дополнительный внешний вызов; сложнее повторяемо тестировать условия повтора | Обязательные: соблюдает; Предпочтения: хуже из-за лишнего вызова и усложнения |
| C | Нет дополнительных внешних вызовов; можно дать ограниченную пользу локально | Появляется локальная логика, риск переусложнения; важно не нарушить QA-1 | Обязательные: соблюдает при аккуратной формулировке; Предпочтения: средне |

Дерево подвариантов (до 10 узлов):
- Корень: «Как обработать timeout или исключение внешнего LLM?» — проверка обязательных: N/A; статус: раскрыть.
- A: Контролируемый ответ без повторов — обязательные: OK (REL-1, OUT-1, QA-1, SCOPE-1); + просто; - возможна путаница с пустыми `risks`; статус: оставить. Ссылка: CASE REL-1/OUT-1/QA-1/SCOPE-1.
- B: Один автоповтор, затем контролируемый ответ — обязательные: OK; + шанс получения содержимого; - лишний внешний вызов; статус: оставить. Ссылка: CASE REL-1/OUT-1.
- C: Локальные детерминированные проверки, без нового LLM — обязательные: OK при отсутствии неподтверждённых рисков (QA-1); + без внешних вызовов; - добавляет локальную логику; статус: оставить. Ссылка: CASE QA-1/SCOPE-1.
- A1: Summary явно сообщает о недоступности LLM; `risks` = []; `checks` указывают ручную проверку и повтор позже; явная оговорка, что пустые `risks` не подтверждают безопасность — обязательные: OK; + максимальная ясность; - пользы от анализа нет; статус: кандидат для выбора. Ссылки: REL-1/OUT-1/QA-1.
- A2: Summary указывает тип сбоя (timeout/exception); `risks` = []; `checks` включают воспроизводимую проверку REL-1 (как эмулировать таймаут/исключение) — обязательные: OK; + ясность и сразу чек-лист; - больше деталей; статус: оставить. Ссылки: REL-1/OUT-1.
- B1: Повтор только при timeout; при иных исключениях сразу контролируемый ответ — обязательные: OK; + ограничение лишних вызовов; - ветвление логики; статус: оставить. Ссылки: REL-1.
- B2: Один повтор при любом сбое вызова LLM (timeout/исключение), затем контролируемый ответ — обязательные: OK; + единообразие; - лишний вызов и латентность; статус: оставить. Ссылки: REL-1.
- C1: Минимальные локальные проверки: только корректный OUT-1 и явное предупреждение; `risks` = []; `checks`: ручная проверка — обязательные: OK; + просто, без лишних вызовов; - ценность минимальна; статус: оставить. Ссылки: OUT-1/QA-1.
- C2: Расширенные локальные проверки: дополнительно детерминированные проверки правил (например, API-1/422/413 в суммарном сообщении), без добавления `risks` — обязательные: OK; + больше контекста; - усложнение логики; статус: оставить. Ссылки: CASE API-1, OUT-1.

Порядок BFS: Корень → A → B → C → A1 → A2 → B1 → B2 → C1 → C2.

Краткие оценки конечных узлов:
- A1 — соответствует всем обязательным; предпочтения: лучшая ясность, отсутствие лишних вызовов, проверка легко формализуется. Статус: кандидат для выбора.
- A2 — соответствует обязательным; предпочтения: ясно, чуть сложнее из-за разделения по типу сбоя. Статус: оставить.
- B1 — соответствует обязательным; предпочтения: добавляет вызов при timeout, усложняет проверку. Статус: оставить.
- B2 — соответствует обязательным; предпочтения: наихудший по «без лишних вызовов» и латентности. Статус: оставить, но не кандидат.
- C1 — соответствует обязательным; предпочтения: без лишних вызовов, но ценность ниже A2; ясность зависит от текста. Статус: оставить.
- C2 — соответствует обязательным; предпочтения: больше логики без явной необходимости в первом сценарии. Статус: оставить.

Проверка предварительного кандидата (A1):
- Сценарий timeout LLM: ожидаем контролируемый OUT-1; summary: «LLM недоступен (timeout); автоматический анализ не выполнялся»; `risks` = []; `checks` указывают ручную проверку и возможность повтора позже. Соответствие: REL-1/OUT-1/QA-1 — да.
- Сценарий исключение LLM: аналогично timeout; соответствие: REL-1/OUT-1/QA-1 — да.
- Отсутствие полученного результата ревью: трактуем как сбой канала LLM; возвращаем тот же контролируемый OUT-1; соответствие — да (REL-1).
- Риск ложной трактовки пустого `risks`: смягчено явным текстом в summary, что пустой список не подтверждает безопасность; соответствие QA-1 — да.
- Дополнительные условия ветви: нет повторных вызовов; границы SCOPE-1 соблюдены; логирование не затрагивается (OBS-1 вне рамки выбора, остаётся по ADR).

Журнал backtracking: Backtracking не потребовался: оснований отклонять кандидата не обнаружено. Условие для возврата: если потребуется повышать шанс получения содержимого без участия пользователя, рассмотреть B1 (один повтор при timeout) как ближайшую альтернативу.

## Выбор

- Выбранная альтернатива: A1.
- Почему: выполняет обязательные правила (REL-1, OUT-1, QA-1, SCOPE-1), минимальна по сложности, не добавляет внешних вызовов, формулирует ясное сообщение, устраняющее риск неверной интерпретации пустых `risks`. Воспроизводимая проверка легко описывается.
- Как проверим (не выполненные тесты):
  1. Вход: корректный diff; условие: искусственно спровоцировать timeout внешнего LLM. Ожидаемый результат: HTTP-ответ в формате OUT-1; `summary` содержит указание на недоступность LLM и оговорку про `risks`; `risks` = []; `checks` включает ручную проверку.
  2. Вход: корректный diff; условие: исключение при вызове LLM. Ожидаемый результат: аналогично (контролируемый OUT-1).
  3. Вход: корректный diff; условие: «нет результата ревью» (например, пустой ответ от LLM). Ожидаемый результат: трактуется как ошибка; контролируемый OUT-1 как выше.
  4. Негативный контроль QA-1: убедиться, что при сбое не добавляются «risks» без evidence из diff/правил; `risks` остаётся пустым.
 - Предложение для ADR (не внесено): «При таймауте или исключении внешнего LLM возвращать контролируемый ответ в формате OUT-1: `summary` явно сообщает, что автоматический анализ не выполнялся и пустой `risks` не подтверждает безопасность; `risks` = []; `checks` указывают ручную проверку и возможность повторного запроса позднее. Автоматических повторов не выполнять в первом сценарии.»
