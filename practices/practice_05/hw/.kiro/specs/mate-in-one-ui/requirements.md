# Требования: веб-тренажёр «Мат в один ход»

## Введение и статус

Пользователю нужен простой интерфейс для просмотра позиции, выполнения одного хода и получения результата серверной проверки.

Статус: требования обновлены по утверждённому контракту и представлены пользователю для проверки; сами требования пока не утверждены. Проектирование, задачи реализации и написание кода не начаты.

Основание: [утверждённый общий контракт API](../../contracts/mate-in-one-api.md), утверждён пользователем 28 октября 2026 года. Форматы обмена, HTTP-статусы и порядок ошибок определяет контракт; этот документ фиксирует обязанности UI без изменения контракта.

## Границы и смежные ожидания

- Включено: загрузка каталога и позиции, доска, выбор клеток, серверное уточнение превращения, три результата, повторные попытки, пропуск и следующая задача, завершение просмотра, ошибки и ручные повторы.
- Исключено: регистрация, авторизация, база данных, история и сохранение прогресса, генерация задач, полноценная партия, подсказки решения, подсветка допустимых ходов и сложный дизайн.
- UI не определяет допустимость хода, необходимость превращения, шах или мат. Разбор FEN нужен только для отображения позиции и стороны хода.
- Backend предоставляет каталог ровно из пяти пригодных задач в стабильном порядке, исходные FEN и независимую оценку попыток. Выбор конкретных пяти позиций остаётся открытым вопросом backend и не меняет контракт.
- Ограничения: frontend на HTML, CSS и JavaScript; UI и API обслуживаются Flask с одного origin. Клиент использует относительный /api/v1. Разные origins и CORS не входят в утверждённую схему; UI не открывается через file://.

## Требования

### 1. Загрузка и отображение задачи

**Цель:** пользователь видит исходную позицию и понимает, какой стороне нужно поставить мат.

#### Критерии приёмки

1. When пользователь открывает тренажёр, the MateInOneUI shall получить каталог и запросить позицию первого элемента в порядке каталога.
2. While каталог или исходная позиция загружается, the MateInOneUI shall показывать состояние загрузки и блокировать отправку хода.
3. When позиция успешно получена, the MateInOneUI shall показать доску 8×8 с фигурами из исходного FEN, ID задачи, текст «Мат в один ход» и сторону хода из FEN.
4. While задача отображается, the MateInOneUI shall располагать белых снизу, клетку a1 слева внизу и показывать однозначные координаты клеток независимо от стороны хода.
5. If задача ещё не получена либо ответ не соответствует контракту, the MateInOneUI shall не разрешать отправку попытки для этой позиции.

### 2. Выбор хода и фигуры превращения

**Цель:** пользователь передаёт серверу выбранный ход, не полагаясь на шахматную проверку в UI.

#### Критерии приёмки

1. When пользователь нажимает на фигуру без предварительного выбора, the MateInOneUI shall выбрать и визуально выделить исходную клетку.
2. When пользователь повторно нажимает на выбранную исходную клетку, the MateInOneUI shall отменить выбор без отправки запроса.
3. When пользователь нажимает на пустую клетку без выбранной фигуры, the MateInOneUI shall не отправлять запрос проверки.
4. When пользователь выбирает другую клетку после выбора фигуры, the MateInOneUI shall отправить одну попытку для текущего ID с выбранными from и to и с promotion: null.
5. While запрос выполняется, the MateInOneUI shall показывать ожидание и блокировать повторную отправку, выбор другого хода и переход к следующей задаче.
6. When сервер отвечает 400 PROMOTION_REQUIRED, the MateInOneUI shall предложить выбор фигуры по error.details.choices, сохранив исходную позицию и выбранные клетки.
7. While ожидается выбор фигуры превращения, the MateInOneUI shall не показывать обычную ошибку с кнопкой «Повторить» и не подставлять фигуру автоматически.
8. When пользователь выбирает предложенную фигуру превращения, the MateInOneUI shall отправить новый независимый запрос для того же ID и тех же клеток с выбранным promotion.
9. When сервер возвращает 200 correct или incorrect для обычного хода с promotion: null, the MateInOneUI shall обработать результат по разделу 3 без выбора фигуры превращения.
10. When пользователь формирует попытку, the MateInOneUI shall передать её серверу без локального определения допустимости, необходимости превращения или мата, включая выбор чужой фигуры и занятой клетки назначения.

Два последовательных запроса при уточнении превращения предусмотрены контрактом и не считаются дублированием одной отправки.

### 3. Результат проверки и повторная попытка

**Цель:** пользователь различает решение, допустимый неверный ход и недопустимый ход.

#### Критерии приёмки

1. When сервер возвращает 200 correct, the MateInOneUI shall показать «Правильно! Мат в один ход» и позицию из серверного fen_after.
2. While текущая задача имеет подтверждённый результат correct, the MateInOneUI shall блокировать новые попытки этой задачи и сохранять доступность кнопки «Следующая задача» вне ожидания запроса.
3. When сервер возвращает 200 incorrect, the MateInOneUI shall показать «Неправильно. Попробуйте ещё раз», сохранить исходную позицию и сбросить выбор клеток.
4. When сервер возвращает 200 illegal, the MateInOneUI shall показать «Недопустимый ход. Выберите другой ход», сохранить исходную позицию и сбросить выбор клеток.
5. When получен incorrect или illegal, the MateInOneUI shall разрешить новую попытку относительно исходной позиции.
6. While серверный результат ещё не получен, the MateInOneUI shall не показывать подтверждение правильности хода.
7. When отображается любой результат, the MateInOneUI shall обозначать его текстом, позволяющим различить результат без опоры только на цвет.

fen_after возвращается для correct и incorrect, а для illegal равен null. UI применяет его к доске только после correct. Сервер принимает любой допустимый матующий ход; шах без мата и пат относятся к incorrect.

### 4. Следующая задача и завершение просмотра

**Цель:** пользователь проходит каталог в заданном порядке и может пропускать задачи.

#### Критерии приёмки

1. When пользователь нажимает «Следующая задача» и следующий элемент каталога существует, the MateInOneUI shall запросить позицию этого элемента независимо от решения текущей задачи.
2. When позиция следующей задачи успешно получена, the MateInOneUI shall заменить текущую задачу и очистить предыдущий результат и выбор клеток.
3. If загрузка следующей задачи завершилась ошибкой, the MateInOneUI shall сохранить предыдущую задачу и целевой ID для повтора без дополнительного продвижения.
4. When пользователь открывает последнюю задачу каталога, the MateInOneUI shall сохранить возможность её решения до correct либо явного завершения просмотра.
5. When пользователь нажимает «Следующая задача» на последнем элементе каталога, the MateInOneUI shall показать «Задачи закончились» и завершить просмотр и попытки этого прохождения без запроса несуществующей задачи.
6. When показано окончание каталога, the MateInOneUI shall не утверждать, что все задачи решены, поскольку пропуски разрешены.
7. When выбирается следующая задача, the MateInOneUI shall определять её по фактически полученному порядку каталога, без встроенного числа 5 в правилах навигации.
8. If сервер возвращает 404, the MateInOneUI shall обработать его как ошибку обращения, а не как окончание каталога.

### 5. Ошибки, ожидание и повтор запросов

**Цель:** пользователь понимает сбои обмена и может продолжить работу без потери текущей позиции.

#### Критерии приёмки

1. If соединение отсутствует, запрос завершается сетевым сбоем либо ответом 5xx, the MateInOneUI shall показать сообщение о сбое и действие ручного повтора, сохранив имеющуюся задачу.
2. If за 10 секунд от начала запроса не получен полный ответ, the MateInOneUI shall прекратить ожидание, снять временную блокировку и предложить ручной повтор.
3. When пользователь повторяет неудавшийся запрос, the MateInOneUI shall сохранить его метод, целевой ID и тело, включая выбранную фигуру превращения при её наличии.
4. When пользователь повторяет загрузку следующей задачи, the MateInOneUI shall запросить тот же целевой ID без дополнительного перехода вперёд.
5. If сервер возвращает ошибку приложения, the MateInOneUI shall различать её по error.code, а не по тексту message.
6. If получен 4xx кроме PROMOTION_REQUIRED, the MateInOneUI shall показать ошибку обращения без автоматического повтора и без шахматного результата; повтор требует исправления обращения.
7. If ответ имеет неожиданный формат, неизвестный статус результата или несоответствие контракту, the MateInOneUI shall показать ошибку обмена с возможностью ручного повтора, сохранив имеющуюся позицию.
8. If получен ответ устаревшего запроса, the MateInOneUI shall не менять актуальную задачу, результат новой попытки или выбор превращения, в том числе для запросов с одинаковым task_id.
9. When запрос завершился ответом, ошибкой или тайм-аутом, the MateInOneUI shall снять временную блокировку действий, сохранив запрет новых попыток после correct и после завершения просмотра.
10. If произошла сетевая ошибка, локальный тайм-аут или ошибка HTTP, the MateInOneUI shall не представлять её как correct, incorrect либо illegal.
11. When действие требует повторного запроса после сбоя, the MateInOneUI shall выполнять повтор только по явному действию пользователя.

Отмена ожидания не подтверждает остановку обработки сервером. Повторы не создают историю и не изменяют исходные позиции; отдельный ключ идемпотентности не требуется. При восстановлении соединения ручной повтор должен позволять продолжить работу без перезагрузки страницы.

### 6. Простота и доступность интерфейса

**Цель:** пользователь решает задачи без учётной записи и сложного управления.

#### Критерии приёмки

1. When пользователь открывает тренажёр, the MateInOneUI shall предоставлять основные действия без регистрации, авторизации и ввода учётных данных.
2. When пользователь работает мышью или касанием, the MateInOneUI shall позволять выбрать фигуру, клетку назначения и предложенную фигуру превращения.
3. While ширина окна равна 360 или 1280 пикселям, the MateInOneUI shall показывать доску, текущую задачу, результат и основные кнопки без перекрытия и горизонтальной прокрутки страницы.

## Согласованный обмен: ссылка и обязательные уточнения

Полные схемы и примеры находятся в [контракте](../../contracts/mate-in-one-api.md), разделы 2–10. Этот раздел не вводит альтернативных форматов.

| Действие | Метод и маршрут | Данные |
| --- | --- | --- |
| Каталог | GET /api/v1/tasks | tasks: массив объектов id, ровно пять уникальных ID, стабильный порядок |
| Позиция | GET /api/v1/tasks/{task_id} | id и полный шестипольный fen; сторона хода извлекается из FEN |
| Попытка | POST /api/v1/tasks/{task_id}/attempts | Ровно from, to, promotion; Content-Type application/json |
| Результат | HTTP 200 | task_id, result, fen_after |
| Ошибка | HTTP 400/404/405/415/500/503 | error с code, русским message и объектом details |

from и to — строки a1–h8 в нижнем регистре. promotion — null либо q/r/b/n. ID передаётся только в маршруте; клиентский FEN, UCI и другие поля в тело не включаются. Рокировка задаётся перемещением короля, взятие на проходе — перемещением пешки. Отдельных маршрутов /next и завершения нет.

Категории ошибок: INVALID_JSON — 400; INVALID_REQUEST — 400 при отсутствующих/лишних полях, неверной структуре или типах; INVALID_MOVE_FORMAT — 400 при неверной строке координаты или фигуры; PROMOTION_REQUIRED — 400 с choices: [q, r, b, n]; TASK_NOT_FOUND и ROUTE_NOT_FOUND — 404; METHOD_NOT_ALLOWED — 405; UNSUPPORTED_MEDIA_TYPE — 415; INTERNAL_ERROR — 500; SERVICE_UNAVAILABLE — 503. Одинаковые клетки и лишнее превращение при обычном ходе дают 200 illegal, если запись полей корректна. details равен пустому объекту для ошибок, кроме PROMOTION_REQUIRED. В ошибке нет result и fen_after.

Смежное ожидание о приоритете ошибок: маршрут/метод → доступность набора → существование ID → Content-Type → разбор JSON → структура/типы → формат хода → шахматная проверка. Если набор недоступен для проверки ID, ожидается 503. Если набор доступен, но ID отсутствует, ожидается 404 до проверки тела, в том числе при повреждённом JSON. Для GET применяются релевантные шаги. Если процесс недоступен, JSON-ответ не гарантируется.

При promotion: null обычный допустимый ход без превращения получает HTTP 200 с correct при мате либо incorrect при отсутствии мата и с fen_after. Только если обычный ход недопустим, но между теми же клетками существует допустимое превращение, сервер возвращает 400 PROMOTION_REQUIRED. Если нет ни допустимого обычного хода, ни допустимого превращения, сервер возвращает 200 illegal с fen_after: null. Отсутствие превращения само по себе не означает illegal. UI открывает выбор фигуры только по PROMOTION_REQUIRED и использует details.choices; шахматную проверку самостоятельно не выполняет.

## Изменения после согласования 28 октября 2026 года

1. Добавлена ссылка на утверждённый контракт; прежние вопросы API заменены его решениями. Утверждение контракта отделено от проверки этих требований.
2. Загрузка начинается с упорядоченного каталога и первой позиции; используются ID, полный FEN и постоянный текст задания без title.
3. Уточнены строгая схема from/to/promotion и серверный выбор превращения через PROMOTION_REQUIRED и details.choices; исключено общее сообщение с «Повторить» для этого случая.
4. Зафиксированы correct/incorrect/illegal, обязательный fen_after и применение позиции только после correct.
5. Следующая задача выбирается UI; конец определяется по явному нажатию на последней задаче, без /next и без трактовки 404 как окончания.
6. Добавлены классификация и приоритет ошибок, тайм-аут 10 секунд, ручные повторы того же запроса и защита от устаревших ответов отдельных попыток.
7. Закреплены один origin Flask и относительный /api/v1; шахматная логика, список допустимых ходов, сессии и история исключены из UI.
8. Заголовки требований нормализованы: прежним R1–R6 соответствуют разделы 1–6. Критерии представлены в EARS; независимый снимок до согласования сохранён в before-agreement.
9. По исправленному разделу 6 контракта уточнён обычный ход с promotion: null: он получает correct или incorrect при допустимости; отсутствие превращения не означает illegal. Выбор фигуры открывается только по PROMOTION_REQUIRED; неоднозначное «иначе сервер возвращает illegal» удалено.

## Проверка и следующий этап

Проверка выполнена в основном контексте: числовые ID, EARS для всех критериев, покрытие сценариев и ошибок, соответствие контракту и границам UI. Проектная документация steering отсутствует; источниками служат brief и утверждённый контракт. Требования представлены пользователю для проверки. До их утверждения перехода к проектированию, задачам реализации и коду нет.
