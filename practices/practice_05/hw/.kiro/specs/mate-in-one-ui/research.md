# Исследование и решения: mate-in-one-ui

## Сводка
- Дата: 28 октября 2026 года.
- Тип discovery: полный для новой функции; проведён в основном контексте без субагентов, поскольку исходники отсутствуют и объём ограничен.
- Основания: [требования](requirements.md), [утверждённый контракт](../../contracts/mate-in-one-api.md), [brief](brief.md).
- Требования явно утверждены пользователем в текущем сообщении; старое описание их статуса в prose не является отзывом утверждения. spec.json отражает approved=true.
- Ключевые результаты: достаточно нативного JavaScript без шахматных библиотек; PROMOTION_REQUIRED является отдельным исходом; deadline охватывает тело ответа; requestId нужен даже между попытками одной задачи.
- Steering отсутствует, поэтому соответствие неизвестным стандартам проекта не утверждается.

## Журнал исследования

### Локальное состояние и границы
- Прочитаны metadata, требования и brief UI, общий контракт с исправленным разделом 6; проверено наличие прежнего design/research и основных steering.
- Исходников приложения, прежних UI design/research и core steering нет. Смежная backend-спецификация есть; её файлы не редактируются.
- Использованы kiro-spec-design и локальные design-principles, design-discovery-full, design-synthesis, design-review-gate; структура design/research взята из шаблонов проекта.
- Применено: явная граница, File Structure Plan, направление импортов, типизированные контракты, трассировка 44 критериев и проверка до записи.
- Другие локальные domain skills не соответствуют задаче: Sites предназначен для создания сайта через отдельный сервис; здесь документируется существующий локальный проект с фиксированным Flask-контрактом. Код и сайт не создаются.

### Fetch, HTTP-ошибки и чтение тела
- Источник: [MDN Using Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch), проверено 28 октября 2026 года.
- Fetch не отвергает promise только из-за 404; HTTP-статус проверяется отдельно. Чтение JSON асинхронно, получение заголовков ещё не означает чтения полного тела.
- Решение: ApiClient сохраняет HTTP/code, не превращает 400 с PROMOTION_REQUIRED в общий catch; timeout действует до полного получения и проверки ответа.
- Классификация UI соответствует контракту; HTML от инфраструктуры не считается шахматным результатом.

### Отмена и гонки
- Источник: [MDN AbortController.abort](https://developer.mozilla.org/en-US/docs/Web/API/AbortController/abort), проверено 28 октября 2026 года.
- AbortController позволяет отменять запрос и чтение тела. Это клиентская отмена, а не подтверждение остановки обработки на сервере.
- Решение: deadline и abort дополняются инвалидированием requestId. Старые catch/finally не должны менять текущую фазу, сообщение и блокировки.
- requestId монотонный на каждый запрос; taskEpoch отделяет переходы между задачами. Для повтора сохраняется неизменяемая Operation.

### ES modules и Flask
- Источники: [MDN JavaScript modules](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules), [Flask Quickstart](https://flask.palletsprojects.com/en/stable/quickstart/#static-files), проверены 28 октября 2026 года.
- Модули загружаются через сервер с JavaScript MIME. Flask поддерживает раздачу статических файлов.
- Решение: frontend сохраняется отдельным каталогом, Flask отдаёт index на / и ресурсы на /static/ui; API остаётся /api/v1. Настройка раздачи принадлежит backend, не UI.
- Нет CORS, отдельного frontend-dev-server, CDN, сборщика и дополнительных runtime-пакетов. Точная версия Flask остаётся в backend; этот документ не меняет серверные зависимости.
- Поддержку актуального браузера с использованными нативными возможностями подтверждают в будущем браузерном прогоне; обещаний для устаревших браузеров нет.

### Контракт FEN и превращения
- Авторитетный источник: разделы 4–8 общего контракта.
- UI читает расположение и очередь для представления; синтаксические проверки не являются шахматной валидацией.
- Обычный допустимый ход с promotion:null даёт correct/incorrect. Только серверный PROMOTION_REQUIRED открывает выбор; отсутствие превращения не подразумевает illegal.
- fen_after используется для отображения только после correct; при остальных результатах исходная доска сохраняется.

### Модульные проверки без пакетов
- Источник: [Node.js test runner](https://nodejs.org/api/test.html), проверен 28 октября 2026 года.
- Встроенный node:test позволяет не вводить тестовый npm-framework. ESM-режим frontend задаётся метаданными package.json; браузерные DOM-проверки выполняются отдельным стендом через Flask в разработке.
- Это план проверок, а не установленная зависимость или уже исполненный тест.

## Оценка архитектурных вариантов
| Вариант | Плюсы | Ограничения | Решение |
| --- | --- | --- | --- |
| Один большой JS-файл | Мало файлов | Сеть, DOM и гонки связаны, трудно независимо проверять | Отклонён |
| Нативные модули и один Controller | Явные границы, без сборки и внешних зависимостей | Ручная строгая проверка небольших DTO | Выбран |
| UI-фреймворк и библиотека доски | Готовые UI-примитивы | Лишние зависимости и риск шахматной логики, не нужны для 64 кнопок | Не принимаются в текущий объём |

Это оценка применимости архитектуры, а не утверждение о конкретных сторонних библиотеках. Их версии и возможности не заявляются, поскольку зависимости не добавляются.

## Решения дизайна

### Обобщение: операция и результат запроса
Три вида запросов используют один контекст deadline/requestId и единый ApiOutcome. При этом формы catalog/task/result/promotion остаются раздельными типами; универсальный HTTP-framework не создаётся. Генерализация ограничена текущими тремя маршрутами.

### Build vs adopt: нативная платформа
Переиспользуются Fetch, AbortController, DOM-кнопки, CSS Grid и ES modules. Своими остаются только Controller конечного состояния, проверка конкретных JSON-форм и преобразование FEN в клетки. Шахматная библиотека не принимается: UI запрещено вычислять правила, а представлению достаточно символов фигур и координат.

### Упрощение: единственное состояние
Controller владеет состоянием; отдельный store, event bus, кеш задач и persistence не нужны. DOM не становится источником истины. View получает готовую модель; ApiClient не знает индекса следующей задачи. Нет оптимистического перемещения и отката сложной позиции.

### Интеграционная граница
Файлы UI размещаются в frontend; серверная раздача и Python-маршруты остаются backend. Эта зависимость описана явно до интеграции. Выбор конкретных учебных позиций не заменяется иллюстративными FEN из контракта.

## Риски и меры
- Задержанное тело после быстрых заголовков — таймер до чтения и fake-clock тест.
- Старый ответ после повтора той же задачи — requestId, taskEpoch и охрана всех терминальных путей.
- PROMOTION_REQUIRED ошибочно попадает в общее сообщение — отдельный discriminant и тест промежуточного выбора.
- Ошибочная трактовка null как illegal — отдельный обычный correct/incorrect сценарий.
- Ошибка загрузки следующей задачи пропускает позицию — targetIndex отдельно, commit после успешной проверки.
- Шахматные правила проникают в FEN-парсер — только синтаксис и представление, проверка границ на review.
- Символы фигур плохо видны на одной клетке — проверка обоих цветов/фонов, доступные текстовые подписи.
- Неизвестная структура будущего Flask-проекта — раздача отдельного frontend-каталога без владения Python-файлами.
- Конкретные пять задач ещё не выбраны — UI проверяется на фикстурах; реальная приёмка зависит от готовности backend.
- URL сегмент с произвольным ID — encodeURIComponent; фактическая передача ID через Flask проверяется интеграционно без введения нового ограничения схемы.

## Результат синтеза и review
Полный discovery завершён без установки пакетов. Основные выводы перенесены в design.md. Механические проверки: 44/44 критериев представлены; разделы границ заполнены; конкретные пути и компоненты согласованы; заглушки шаблона отсутствуют. Содержательно проверены исправленное превращение, разделение ошибок и результатов, завершение последней задачи, state transitions, независимость повторов и возможность реализации по ограниченным файлам.

При первом review исправлено локальное противоречие: некорректный envelope 4xx относится к protocolError с возможностью ручного повтора по 5.7, а требование исправить обращение относится к распознанным 4xx. Добавлены явные типы ValidationResult, ClockPort и resumePhase; повторная проверка границ и покрытия пройдена. Реальной неоднозначности требований не обнаружено.

Результат проверки означает готовность черновика дизайна к просмотру, а не утверждение дизайна и не успешные тесты приложения. В этом этапе исполняемых исходников нет.
