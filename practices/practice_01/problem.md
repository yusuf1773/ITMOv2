# Проблема и метрики

## Проблема

- Пользователь: инженер-ревьюер или автор PR, отправляющий diff через API для получения подсказок по ревью. Источник: CASE.md.
- Ситуация: сервис принимает diff и должен вернуть краткое описание, до 3 рисков с evidence и список проверок. Источник: CASE.md «Задача помощника».
- Что происходит сейчас: реализован endpoint `POST /api/reviews`, который без валидации извлекает `payload["diff"]` и вызывает LLM синхронно; сервис возвращает `{ "comment": answer }`. Источник: TRAINING_PR.diff (app/api.py:35–38; app/review_service.py:19–22).
- Почему это мешает пользователю или бизнесу: отсутствует соответствие формату OUT-1; возможны 500 при отсутствии поля `diff`; нет ограничений API-1 и sanitation SEC-1; нет таймаута и контролируемых ошибок по REL-1; следовательно, ответы нестандартизированы, риски не структурированы, а сервис ненадёжен. Источник: CASE.md «Правила репозитория», TRAINING_PR.diff.
- Что не входит в задачу: автоматическое принятие решений (approve/merge), модификация кода, действия в GitHub, любые изменения вне одного PR-диффа. Источник: CASE.md (SCOPE-1).

## Метрики

Выберите измеримые показатели, относящиеся к проблеме. Не используйте VTG, IRR, WACC, CSAT или другую метрику только ради названия.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Доля ответов в формате OUT-1 (summary, risks<=3, checks) | 0%: текущий сервис возвращает только `comment`. Проверяем процент ответов, соответствующих OUT-1, на тестовом наборе diff. | 100% к завершению сценария | На каждом релизе первого сценария | Автотесты и ручная проверка по OUT-1 |
| Ошибки 500 при отсутствии поля `diff` | Наблюдается: KeyError -> 500. Измеряем долю запросов без `diff`, завершающихся 500. | 0% (ожидаем 422/413 по правилам) | После добавления валидации | Логи и e2e-тест без поля `diff` |
| Ограничение длины diff (API-1) | Не реализовано: запросы >20 000 символов проходят. | 100% запросов >20 000 символов получают 413 | После внедрения ограничения | Нагрузочный тест с synthetic diff |
| Таймаут LLM-вызова (REL-1) и контролируемый ответ | Не реализовано. | 100% таймаутов/исключений завершаются контролируемым ответом без 500 | После внедрения таймаута | Интеграционный тест с заглушкой LLM |
| Удаление секретов (SEC-1) | Не реализовано. | 100% тестовых секретов редактируются до [REDACTED] перед LLM | После внедрения редактирования | Unit/интеграционный тест с диффом, содержащим «token=...», «PRIVATE KEY» |

## Почему изменение метрики подтвердит решение проблемы


- Формат OUT-1 гарантирует пригодность ответа для человека-ревьюера; достижение 100% по этой метрике означает соблюдение основного контрактного результата.
- Снижение 500 при отсутствии `diff` до 0% подтверждает корректную валидацию входа и устойчивость API.
- 413 для длинных diff демонстрирует соблюдение границы API-1 и защиту от DoS-класса проблем.
- Контролируемая обработка таймаутов REL-1 показывает, что сервис не «падает» при сбоях LLM и даёт предсказуемый отклик.
- Редактирование секретов (SEC-1) снижает риск утечек; unit/integration-evidence подтверждают наличие механизма.

## Как использовали AI

- Для чего: формализовать проблему и подобрать измеримые метрики, сопоставив их с правилами CASE.md и состоянием TRAINING_PR.diff.
- Тип промпта: master prompt (структурирование контракта и метрик); без генерации кода.
- Строка в [`prompts.md`](prompts.md): P1-02 (Master Prompt v1).
- Что проверили и исправили сами: свели каждую метрику к конкретному правилу (OUT-1, API-1, REL-1, SEC-1) и проверяемому сценарию; исключили неподтверждённые метрики; добавили способ замера через тесты и логи.
