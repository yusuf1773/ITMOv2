# Brief: mate-in-one-backend

Статус: черновик для обсуждения. Требования не утверждены. API предварительный и не согласован с UI-командой. Реализация не начата.

## Проблема
Веб-тренажёру «Мат в один ход» нужен backend, который выдаёт позиции и достоверно проверяет попытки. UI разрабатывает другая команда и не должен реализовывать шахматные правила.

## Текущее состояние
В папке проекта есть инструкции и навыки Kiro. Спецификации и основные steering-документы отсутствуют; программного кода в корне нет. Выбран путь C: одна новая спецификация backend.

## Желаемый результат
Backend предоставляет пять задач, проверяет ход относительно исходной позиции выбранной задачи и различает мат, допустимый ход без мата и недопустимый ход. Ошибки запроса и неизвестные задачи имеют отдельные ответы.

## Подход
Предварительная основа из запроса: Python, Flask, python-chess, локальный JSON. Окончательное устройство API требует обсуждения.

Варианты границы сервера и UI:
1. Тонкий API: FEN задачи и результат проверки. Малый объём, но UI может потребоваться самостоятельно вычислять обновлённую позицию.
2. API с результатом и FEN после допустимого хода. Малый объём; рекомендуемый черновой вариант, поскольку UI может отрисовать готовое состояние без шахматных правил.
3. Дополнительно выдавать список допустимых ходов для подсветки. Средний объём; включать только при подтверждённой потребности UI.

Выбор варианта 2 — рекомендация для обсуждения, не утверждённое решение.

## Границы
Включено: загрузка и проверка набора задач, выдача данных, проверка попыток, единообразные ошибки API.
Исключено: БД, регистрация и авторизация, Stockfish, серверные пользовательские сессии, история и статистика, генерация задач, полноценная шахматная партия, разработка UI.

## Кандидаты границ ответственности
- Данные: локальный набор задач, уникальные идентификаторы, валидные позиции.
- Шахматная проверка: допустимость хода и мат после него.
- HTTP API: форматы запросов, ответов и ошибок.
- UI-команда: доска, ввод хода, отображение результата, локальный прогресс.
Эти части остаются внутри одной спецификации backend; отдельная спецификация frontend здесь не создаётся.

## Вне ответственности
Backend не определяет дизайн, анимации и пользовательские сценарии интерфейса. Новая попытка не продолжает предыдущую: всегда проверяется исходный FEN задачи.

## Зависимости и потребители
Upstream: согласованный набор пяти задач, Python/Flask/python-chess, решения по контракту с UI.
Downstream: команда интерфейса и интеграционные проверки.

## Существующие спецификации
Расширяемые: нет. Смежные: не обнаружены.

## Ограничения
Python + Flask + python-chess; локальный JSON; без БД, регистрации, Stockfish и хранения пользовательских сессий. На этой стадии код не писать. Язык черновика: русский.

## Функциональные требования и критерии приёмки

| ID | Требование | Критерий приёмки |
| --- | --- | --- |
| R1 | Хранить ровно пять задач в локальном JSON. Каждая содержит уникальный непустой строковый id и FEN. | При загрузке доступны ровно пять задач с уникальными id; каждая выдаваемая задача соответствует данным файла. |
| R2 | Проверять пригодность данных до обслуживания запросов. | Отклоняются повреждённый JSON, неверное число задач, дубликаты id, синтаксически неверные или недопустимые шахматные позиции. Для каждой позиции подтверждается наличие хотя бы одного допустимого матующего хода. Позиция не завершена до попытки; ошибка данных явно сообщается при запуске. |
| R3 | Выдавать каталог и исходную позицию выбранной задачи. | Каталог позволяет получить все пять id; запрос известного id возвращает его FEN с очередью хода. Решение и перечень матующих ходов в обычной выдаче отсутствуют. |
| R4 | Проверять допустимость хода на сервере относительно исходной позиции. | Корректно записанный, но недопустимый ход, включая ход чужой фигурой, ход с пустой клетки и ход, оставляющий своего короля под шахом, даёт illegal. |
| R5 | Принимать любой допустимый матующий ход. | Допустимый ход, после которого противнику поставлен мат, даёт correct. При нескольких матующих ходах принимается каждый. |
| R6 | Отличать остальные допустимые ходы. | Допустимый ход без мата даёт incorrect, в том числе обычный шах и пат. |
| R7 | Обрабатывать неизвестные задачи и некорректные запросы отдельно от шахматного результата. | Неизвестный id даёт 404; неверный JSON, отсутствующий или нестроковый ход и неверный синтаксис хода дают 400; неверный Content-Type даёт 415. Ни одна из этих ошибок не маскируется под correct/incorrect/illegal. |
| R8 | Не хранить состояние попыток на сервере. | Повтор одного запроса даёт тот же шахматный результат; попытки разных клиентов не влияют друг на друга; предыдущий ход не изменяет исходную задачу. |
| R9 | Проверять специальные ходы по шахматным правилам. | При соответствующих позициях корректно учитываются превращение, рокировка и взятие на проходе. Очередь хода и права берутся из FEN. Для проверок разрешены дополнительные тестовые позиции вне основного набора из пяти. |
| R10 | Возвращать стабильные машинные ответы. | Все прикладные ответы API имеют application/json; результат — ровно одна строка correct, incorrect или illegal. Ошибка содержит стабильный code и понятный message. Внутренние traceback клиенту не передаются. |

R2: проверка существования матующего хода при подготовке/загрузке данных не означает передачу решения клиенту. Единственность решения не требуется этим черновиком.

## Предварительный API — НЕ СОГЛАСОВАН

Базовый путь-кандидат: /api/v1. Идентификатор задачи — строка.

| Метод и путь | Назначение | Предварительный ответ |
| --- | --- | --- |
| GET /api/v1/puzzles | Список задач | 200, объект с массивом puzzles; элемент содержит id и необязательный title |
| GET /api/v1/puzzles/{id} | Получить задачу | 200, объект с id и fen |
| POST /api/v1/puzzles/{id}/attempts | Проверить попытку | Запрос: объект с полем move в UCI; 200 для любого из трёх шахматных результатов |

Пример тела попытки: {"move":"e7e8q"}. Предлагается UCI: начальная и конечная клетки; при превращении суффикс q/r/b/n обязателен. Пример иллюстрирует только формат и не связан с конкретной задачей.

Пример ответа на допустимый ход: {"result":"correct","fen_after":"<FEN после хода>"}. Здесь <FEN после хода> — пояснительный заполнитель, не значение контракта. При допустимом ходе без мата result равен incorrect. При illegal предлагается {"result":"illegal","fen_after":null}.

Пример ошибки: {"error":{"code":"puzzle_not_found","message":"Задача не найдена"}}.

Предлагаемые коды ошибок: 400 invalid_json / invalid_request / invalid_move_format; 404 puzzle_not_found; 405 method_not_allowed; 415 unsupported_media_type; 500 internal_error. Для неизвестного id на маршруте задачи предлагается приоритет 404 до разбора тела.

Синтаксически правильный, но невозможный ход — illegal, а не ошибка формата. Принимается JSON-объект с move; неизвестные поля предлагается отклонять как invalid_request. Поле fen от клиента не принимается: источник истины — задача на сервере.

200 с incorrect означает успешную проверку допустимого хода без мата, а не ошибку HTTP. Дополнительные is_check и is_checkmate в черновой контракт не включены: result уже сообщает об успешном мате.

## Вопросы к UI-команде

Блокируют согласование контракта:
1. Поддерживает ли библиотека доски исходный FEN и ввод UCI? Нужны ли координаты from/to вместо строки move?
2. Как UI выбирает превращение? Все четыре фигуры или только ферзь? Предложение backend — принимать все допустимые превращения.
3. Нужен ли fen_after для допустимого неправильного хода; когда UI показывает позицию после попытки, а когда возвращает исходную?
4. Нужны ли подсветка допустимых ходов и отдельный серверный список ходов? Кто отвечает за его получение и показ без дублирования правил в UI?
5. Подходят ли названия маршрутов, поля и разграничение 200/400/404/415? Принимается ли различие неверного формата и illegal? Как обрабатывать повторные/запаздывающие ответы?
6. Где размещаются frontend/backend, совпадают ли origin? Нужны ли CORS и какие разрешённые адреса и порты для разработки и размещения?

Уточняют пользовательский сценарий и данные:
7. Как выбирается следующая задача: список, последовательность или случайный выбор на клиенте? Достаточно ли каталога всех пяти?
8. Как определяется ориентация доски? Достаточно ли очереди хода из FEN или нужно отдельное поле?
9. Кто предоставляет и проверяет пять позиций; допустимы ли несколько решений, чёрные на ходу и специальные ходы в учебном наборе?
10. На каком языке UI показывает сообщения? Использует ли собственные переводы по error.code? Какие дополнительные поля задачи нужны: title, описание?
11. Как UI отображает недоступность сервера и даёт повторить запрос? Нужен ли согласованный таймаут и конкретная цель по времени ответа?
